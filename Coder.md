**ТЕХНИЧЕСКОЕ ЗАДАНИЕ**  
**на разработку раздела «Coder» в Open WebUI**  
**Версия:** 1.0  
**Дата:** 15 октября 2026 г.  
**Назначение документа:** определение требований, архитектуры, интерфейсов, порядка разработки и критериев приёмки функциональности, обеспечивающей работу кодового ассистента с последующим экспортом изменений в GitHub.

---

## 1. Общие сведения

### 1.1. Цель создания раздела

Необходимо добавить в Open WebUI специализированный раздел **Coder**, который по пользовательскому опыту и назначению обеспечивает:

1. Работу с языковой моделью в режиме помощника по написанию, правке, рефакторингу, объяснению и тестированию кода.
2. Формирование структурированных изменений в файлах проекта.
3. Предварительный просмотр отличий перед применением изменений.
4. Безопасный экспорт изменений непосредственно в GitHub:
   - создание ветки;
   - коммит одного или нескольких файлов;
   - создание Pull Request;
   - получение ссылок на коммит и PR.
5. Управление подключением GitHub, правами доступа, аудитом действий и настройками администратора.

### 1.2. Ожидаемый результат

По итогам разработки в Open WebUI должен появиться раздел или эквивалентная ему функциональность, позволяющая пользователю вести диалог с кодовой моделью, получать изменения в формате, пригодном для автоматического применения, и в один-два шага отправлять эти изменения в выбранный GitHub-репозиторий.

### 1.3. Термины и определения

| Термин | Определение |
|---|---|
| Open WebUI | Веб-интерфейс и платформенное окружение, в котором реализуется раздел Coder. |
| Раздел Coder | Пользовательская зона Open WebUI, специализированная для работы с кодом и экспортом в GitHub. |
| Change Set | Структурированный набор изменений: создаваемые, изменяемые, удаляемые или переименовываемые файлы. |
| Export Job | Серверная задача экспорта изменений в GitHub. |
| GitHub App | Приложение GitHub, использующееся для авторизации и доступа к репозиториям. |
| OAuth App | Альтернативный способ авторизации пользователя через GitHub OAuth. |
| PAT | Personal Access Token, личный токен доступа GitHub. |
| Diff | Текстовое представление отличий между исходным и изменённым содержимым файлов. |
| PR | Pull Request в GitHub. |
| Исполнитель | Разработчик или команда, реализующая настоящее техническое задание. |

## 2. Допущения и ограничения

### 2.1. Допущения

1. Используется self-hosted или управляемая инсталляция Open WebUI с доступом администратора.
2. Пользователи Open WebUI уже проходят аутентификацию в системе.
3. Целевая интеграция выполняется с GitHub Cloud; поддержка GitHub Enterprise Server является желательной, но может быть вынесена во вторую очередь.
4. Для кодовой генерации используется одна или несколько моделей, доступных в Open WebUI, например специализированные кодовые модели.
5. Текущая версия Open WebUI позволяет нативно добавить новую вкладку/раздел в боковое меню.

### 2.2. Нативный раздел в Open WebUI

Реализуется как полноценный маршрут/раздел, например `/coder`, с собственным интерфейсом, интеграцией в боковое меню, серверными API и хранилищем состояний.

## 4. Нефункциональные требования

| ID | Категория | Требование |
|---|---|---|
| NFR-01 | Безопасность | Секреты GitHub не должны храниться в localStorage, sessionStorage, cookie клиента, логах, ответах API и сообщениях об ошибках. |
| NFR-02 | Безопасность | Шифрование токенов должно выполняться с использованием надёжного симметричного шифрования, например AES-256-GCM, с ключом, недоступным обычным пользователям. |
| NFR-03 | Безопасность | Все серверные эндпоинты Coder должны требовать аутентификацию Open WebUI и проверять принадлежность ресурсов пользователю. |
| NFR-04 | Безопасность | Callback GitHub OAuth/App должен защищаться от CSRF через state-параметр. |
| NFR-05 | Производительность | Загрузка дерева файлов типичного репозитория должна занимать не более 3 секунд при стабильной сети, без учёта скорости GitHub API. |
| NFR-06 | Производительность | Формирование diff для набора до 20 файлов среднего размера не должно превышать 2 секунд на стороне сервера. |
| NFR-07 | Надёжность | Экспорт должен быть идемпотентным: повторный запрос с тем же idempotency key не должен создавать дублирующие коммиты/PR. |
| NFR-08 | Масштабируемость | Длительные операции экспорта должны выполняться асинхронно с отображением статуса задачи. |
| NFR-09 | Сопровождаемость | Код должен быть покрыт модульными и интеграционными тестами; целевое покрытие бизнес-логики — не ниже 80%. |
| NFR-10 | Совместимость | Решение должно работать в актуальных версиях Chrome, Firefox, Safari, Edge. |
| NFR-11 | Наблюдаемость | Необходимо журналировать события, метрики успеха/ошибок, длительность операций и идентификаторы задач без раскрытия секретов. |
| NFR-12 | Конфиденциальность | Пользовательские промпты и содержимое кода не должны переда третьим лицам, кроме GitHub API при явном экспорте и выбранной языковой модели. |
| NFR-13 | Резервное восстановление | Данные подключений и задач экспорта должны участвовать в стандартном бэкапе Open WebUI/БД. |

## 5. Архитектура решения

### 5.1. Высокоуровневая схема

Логически система состоит из следующих компонентов:

1. **Frontend Coder UI**
   - маршрут/панель раздела Coder;
   - чат с моделью;
   - выбор репозитория и ветки;
   - файловое дерево;
   - просмотрщик кода;
   - просмотрщик diff;
   - панель экспорта в GitHub.

2. **Backend Coder Service**
   - API раздела Coder;
   - управление сессиями и проектами;
   - валидация Change Set;
   - формирование diff;
   - оркестрация экспортных задач;
   - аудит.

3. **GitHub Integration Layer**
   - авторизация через GitHub App или OAuth;
   - клиент GitHub REST/GraphQL API;
   - операции чтения репозиториев, деревьев, файлов;
   - операции записи: blob, tree, commit, ref, pull request.

4. **LLM Integration Layer**
   - вызов кодовой модели через Open WebUI;
   - системный промпт Coder;
   - tools/functions для возврата структурированных изменений;
   - парсинг и повторная валидация ответа модели.

5. **Storage Layer**
   - таблицы/коллекции для подключений, проектов, задач экспорта, аудита;
   - зашифрованное хранилище токенов.

### 5.2. Рекомендуемый стек

С учётом типовой архитектуры Open WebUI:

- backend: Python 3.11 / FastAPI / существующий слой БД Open WebUI SQLAlchemy 2 (asyncio) + Alembic: PostgreSQL + Croma для RAG;
- frontend: SvelteKit / Svelte 5 + TS на фронте / существующий UI Open WebUI;
- векторный бэкенд в контейнере - Croma;
- HTTP-клиент GitHub: `httpx` или аналог с поддержкой async, retry, timeout;
- криптография: стандартная библиотека или проверенный crate/модуль шифрования;
- тестирование: pytest, Playwright/Cypress, mock GitHub API;
- всё развернуто в Docker.

## 6. Пользовательские сценарии

### 6.1. Сценарий 1. Подключение GitHub

1. Пользователь открывает раздел Coder.
2. Видит статус «GitHub не подключён».
3. Нажимает «Подключить GitHub».
4. Переходит на страницу авторизации GitHub.
5. Подтверждает запрашиваемые разрешения.
6. Возвращается в Open WebUI.
7. Система сохраняет токен на сервере и отображает имя пользователя/аватар.

### 6.2. Сценарий 2. Выбор репозитория и работа с кодом

1. Пользователь выбирает репозиторий и ветку.
2. Система загружает дерево файлов.
3. Пользователь открывает файл или прикрепляет несколько файлов к контексту.
4. В чате формулирует задачу, например: «Добавь валидацию в `api/users.py` и напиши тесты».
5. Модель возвращает ответ и Change Set.
6. Система показывает diff по затронутым файлам.

### 6.3. Сценарий 3. Экспорт в GitHub

1. Пользователь нажимает «Экспортировать в GitHub».
2. Указывает:
   - имя новой ветки или существующую ветку;
   - сообщение коммита (формируется автоматически);
   - при необходимости заголовок и описание PR.
3. Система проверяет:
   - права пользователя;
   - отсутствие конфликтов;
   - допустимость путей;
   - размер изменений;
   - наличие секретов, если включена проверка.
4. Пользователь подтверждает действие.
5. Backend создаёт branch/commit/PR через GitHub API.
6. UI отображает результат и ссылки.

### 6.4. Сценарий 4. Действия администратора

1. Администратор включает/отключает раздел Coder.
2. Задаёт:
   - допустимые GitHub Org/Repo;
   - максимальный размер файла;
   - запрет/разрешение записи в определённые пути;
   - обязательное создание PR вместо прямого коммита;
   - режим secret scanning;
   - модель по умолчанию для Coder.
3. Просматривает аудит-лог экспортов.

## 7. Требования к пользовательскому интерфейсу

### 7.1. Структура раздела Coder

Рекомендуемая компоновка:

1. **Верхняя панель**
   - название раздела;
   - индикатор подключения GitHub;
   - селектор репозитория;
   - селектор ветки;
   - кнопка настроек/отключения подключения.

2. **Левая панель**
   - дерево файлов;
   - поиск по файлам;
   - избранные/прикреплённые файлы;
   - история проектов, если реализовано.

3. **Центральная панель**
   - чат с моделью;
   - карточки ответов;
   - блоки кода;
   - карточки Change Set;
   - кнопки «Показать diff», «Применить предпросмотр», «Экспортировать».

4. **Правая/нижняя панель**
   - просмотрщик diff;
   - список изменяемых файлов;
   - сводка экспорта;
   - поля для commit message, branch name, PR title/body.

5. **Модальные окна**
   - подключение GitHub;
   - подтверждение экспорта;
   - настройки проекта;
   - просмотр ошибок и деталей задачи.

### 7.2. Обязательные элементы управления

| Элемент | Назначение |
|---|---|
| Connect GitHub | Запуск авторизации |
| Disconnect | Отзыв локального доступа |
| Select repository | Выбор репозитория |
| Select branch | Выбор базовой ветки |
| Refresh tree | Обновление дерева файлов |
| View file | Просмотр содержимого |
| Attach to context | Добавление файла в контекст чата |
| Review changes | Открытие diff |
| Export to GitHub | Запуск экспорта |
| Create PR | Опция создания Pull Request |
| Copy commit link | Копирование ссылки на коммит |
| Open PR | Переход к PR в GitHub |

### 7.3. Состояния интерфейса

Необходимо явно предусмотреть состояния:

- не авторизован в Open WebUI;
- Coder отключён администратором;
- GitHub не подключён;
- подключение в процессе;
- подключение успешно;
- ошибка авторизации;
- нет доступных репозиториев;
- репозиторий загружается;
- файл не поддерживается для просмотра;
- Change Set не распознан;
- Change Set невалиден;
- diff готов;
- экспорт выполняется;
- экспорт успешен;
- экспорт частично успешен;
- экспорт ошибочен;
- токен истёк/отозван;
- недостаточно прав;
- превышен лимит API;
- обнаружен секрет в коде.

### 7.4. Требования к отображению diff

1. Diff должен отображаться в виде Unified Diff или эквивалентного удобочитаемого представления.
2. Изменения не должны передаваться только цветом; необходимы маркеры `+`, `-`, подписи «добавлено/удалено».
3. Для больших файлов должна быть виртуализация или сворачивание неизменённых участков.
4. Пользователь должен видеть:
   - путь файла;
   - тип операции;
   - количество добавленных/удалённых строк;
   - предупреждения, если файл бинарный или превышает лимит.

## 8. Формат Change Set

### 8.1. Назначение

Модель должна возвращать изменения в структурированном JSON-формате, пригодном для серверной валидации и экспорта.

### 8.2. Рекомендуемая JSON-схема

```json
{
  "version": "1.0",
  "summary": "Краткое описание изменений",
  "risk_level": "low|medium|high",
  "tests_recommended": true,
  "files": [
    {
      "path": "src/services/user_service.py",
      "operation": "update",
      "language": "python",
      "content": "полное новое содержимое файла",
      "explanation": "Добавлена валидация email"
    },
    {
      "path": "tests/test_user_service.py",
      "operation": "create",
      "language": "python",
      "content": "import pytest\n...",
      "explanation": "Новые тесты"
    },
    {
      "path": "legacy/old_module.py",
      "operation": "delete",
      "explanation": "Модуль больше не используется"
    }
  ]
}
```

### 8.3. Допустимые операции

| Операция | Описание | Обязательные поля |
|---|---|---|
| create | Создание нового файла | `path`, `content` |
| update | Полная замена содержимого существующего файла | `path`, `content` |
| delete | Удаление файла | `path` |
| rename | Переименование/перемещение | `path`, `from_path` |

На этапе MVP достаточно поддержки `create`, `update`, `delete`. `rename` — Should/Could.

### 8.4. Правила валидации

Сервер обязан проверять:

1. `path` не является абсолютным.
2. `path` не содержит `..`.
3. `path` не начинается с `.git/`.
4. `path` не попадает в запретные шаблоны администратора.
5. Размер `content` не превышает лимит.
6. Суммарный размер всех файлов не превышает лимит экспорта.
7. Бинарные файлы не допускаются, если не включена отдельная поддержка.
8. Для `update` файл существует в базовой ветке, если включён строгий режим.
9. Для `create` файл не должен существовать, если включён строгий режим.
10. Пути нормализуются в POSIX-формат.
11. Кодировка текста — UTF-8.
12. Наличие потенциальных секретов проверяется, если включён secret scanning.

### 8.5. Обработка некорректного ответа модели

Если модель возвращает невалидный JSON:

1. Система должна попытаться извлечь JSON из code fence.
2. При неуспехе — вернуть пользователю понятную ошибку.
3. Опционально — выполнить один автоматический повторный запрос к модели с указанием ошибки формата.
4. Повтор не должен выполняться бесконечно; максимум — 1–2 попытки.

## 9. Интеграция с GitHub

### 9.1. Рекомендуемый способ авторизации

Приоритет: **GitHub App** с пользовательской авторизацией или installation flow.

Преимущества:

- гранулярные разрешения;
- удобнее для организаций;
- легче ротировать секреты;
- не требует классических PAT у каждого пользователя.

Допустимая альтернатива: **GitHub OAuth App**.

Не рекомендуется для production: ручное введение PAT пользователем, если только это не временный MVP и не согласовано отдельно.

### 9.2. Минимальные разрешения

Для GitHub App / OAuth необходимы права как минимум на:

- чтение метаданных репозитория;
- чтение содержимого;
- запись содержимого;
- создание веток;
- создание Pull Request;
- чтение списка репозиториев пользователя/организации.

Для GitHub Classic OAuth scope может потребоваться `repo` или более новые fine-grained equivalents в зависимости от типа приложения. Исполнитель обязан проверить актуальную документацию GitHub на момент реализации.

### 9.3. Поток авторизации

#### OAuth App

1. Frontend вызывает `GET /api/v1/coder/github/auth/start`.
2. Backend генерирует `state`, сохраняет его краткоживуще.
3. Пользователь перенаправляется на GitHub.
4. GitHub возвращает `code` и `state` на callback.
5. Backend проверяет `state`.
6. Backend обменивает `code` на access token.
7. Токен шифруется и сохраняется.
8. Пользователь перенаправляется обратно в `/coder`.

#### GitHub App

1. Пользователь переходит по установке/авторизации приложения.
2. Backend получает installation/user token в соответствии с выбранным режимом.
3. Токен шифруется и привязывается к пользователю Open WebUI.

### 9.4. Хранение токенов

Требования:

- токен хранится только на сервере;
- поле в БД должно быть зашифровано;
- ключ шифрования не должен попадать в репозиторий;
- в логах токены маскируются;
- API не возвращает токен ни при каких условиях;
- при отзыве подключения сервер должен удалить или пометить неактивным токен.

### 9.5. Чтение репозиториев

Необходимые операции:

1. Получить список доступных репозиториев.
2. Получить метаданные репозитория.
3. Получить список веток.
4. Получить дерево файлов по reference.
5. Получить содержимое файла по пути и reference.
6. Проверить права пользователя на запись.

### 9.6. Экспорт изменений в GitHub

Рекомендуемый механизм — использование GitHub Git Database API для атомарного создания коммита с несколькими файлами.

#### Алгоритм экспорта

1. Получить HEAD базовой ветки:
   - `base_ref`
   - `base_commit_sha`
   - `base_tree_sha`

2. Для каждого файла Change Set:
   - создать blob через `POST /repos/{owner}/{repo}/git/blobs`;
   - получить `blob_sha`.

3. Сформировать новое дерево:
   - `POST /repos/{owner}/{repo}/git/trees`
   - с `base_tree = base_tree_sha`;
   - для каждого файла указать `path`, `mode`, `type=blob`, `sha`;
   - для удаления указать `sha=null`.

4. Создать коммит:
   - `POST /repos/{owner}/{repo}/git/commits`
   - `message`
   - `tree = new_tree_sha`
   - `parents = [base_commit_sha]`
   - при необходимости указать author/committer в соответствии с политикой.

5. Создать или обновить ветку:
   - `POST /repos/{owner}/{repo}/git/refs` для новой ветки;
   - или `PATCH /repos/{owner}/{repo}/git/refs/{ref}` для обновления.

6. При необходимости создать Pull Request:
   - `POST /repos/{owner}/{repo}/pulls`
   - `title`
   - `body`
   - `head`
   - `base`

7. Сохранить результат в Export Job:
   - commit SHA;
   - branch name;
   - PR URL;
   - статус;
   - время завершения.

### 9.7. Идемпотентность

Каждый экспорт должен иметь `idempotency_key`, формируемый клиентом или сервером.

Правила:

- повторный запрос с тем же ключом не должен создавать новый коммит/PR;
- если задача уже завершена успешно, возвращается сохранённый результат;
- если задача в процессе, возвращается текущий статус;
- если задача завершилась ошибкой, повтор возможен только с новым ключом или явным сбросом, в зависимости от политики.

### 9.8. Обработка ошибок GitHub

Необходимо различать и корректно отображать:

- 401 — недействительный токен;
- 403 — недостаточно прав, protected branch, rate limit;
- 404 — репозиторий/файл/ветка не найдены;
- 409 — конфликт, например branch already exists;
- 422 — невалидные данные;
- 5xx — ошибка GitHub.

Для rate limit следует использовать заголовки GitHub и применять exponential backoff там, где это безопасно. Повтор записи без идемпотентности запрещён.

## 12. Интеграция с языковой моделью

### 12.1. Системный промпт Coder

Системный промпт должен включать следующие инструкции:

1. Ассистент специализируется на написании, правке, рефакторинге и объяснении кода.
2. Ответы должны быть точными, безопасными и соответствовать стилю проекта.
3. При предложении изменений кода модель обязана возвращать Change Set в заданном JSON-формате.
4. Модель не должна выдумывать несуществующие файлы, если не получает явного указания создать новый файл.
5. Модель должна указывать язык и путь для каждого файла.
6. Модель должна предпочитать полные содержимое файлов для операций `create` и `update`, если иной формат не поддержан системой.
7. Модель должна избегать включения секретов, токенов, паролей, приватных ключей.
8. Если информации недостаточно, модель должна задать уточняющий вопрос вместо генерации опасных изменений.

### 12.2. Tool/Function для модели

Если Open WebUI поддерживает tools/functions, необходимо зарегистрировать инструмент, например:

```json
{
  "name": "coder_prepare_changes",
  "description": "Формирует набор изменений для предпросмотра и экспорта в GitHub",
  "parameters": {
    "type": "object",
    "properties": {
      "summary": {
        "type": "string",
        "description": "Краткое описание изменений"
      },
      "risk_level": {
        "type": "string",
        "enum": ["low", "medium", "high"]
      },
      "files": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "path": {"type": "string"},
            "operation": {
              "type": "string",
              "enum": ["create", "update", "delete", "rename"]
            },
            "language": {"type": "string"},
            "content": {"type": "string"},
            "from_path": {"type": "string"},
            "explanation": {"type": "string"}
          },
          "required": ["path", "operation"]
        }
      }
    },
    "required": ["summary", "files"]
  }
}
```

### 12.3. Контекст репозитория

При запросе модели в контекст следует передавать:

- имя репозитория;
- базовую ветку;
- пути и содержимое прикреплённых файлов;
- ограниченный tree summary, если полный tree слишком велик;
- правила проекта, если доступны: линтеры, форматы, конвенции;
- историю чата в пределах настраиваемого окна контекста.

Необходимо избегать передачи всего репозитория целиком. Использовать выборочное чтение и суммаризацию.

#### Реализованная стратегия прогрессивного контекста (репозитории любого размера, 25+ файлов)

Фиксированный лимит «первые 25 файлов» отменён. Вместо него реализован подход, заимствованный у ведущих агентов кодинга (Qwen Coder, OpenAI Codex, opencode): *map-first, read-on-demand, token-budgeted*.

1. **Полное дерево файлов** всегда передаётся модели (все пути + общее число файлов), независимо от размера репозитория — модель корректно знает структуру проекта.
2. **Скелетная загрузка**: автоматически загружается содержимое ~12 ключевых файлов — корневые документы и манифесты (`README`, `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `Makefile`, `Dockerfile` и т.п.) и по одной точке входа на топ-каталог (`index.*`, `main.*`, `app.*`, `server.*`, `manage.py`, `__init__.py`). Пакетная догрузка выбранных файлов — `POST /api/v1/coder/files/batch` (до 30 путей за запрос).
3. **Бюджет контекста ~48 000 символов** на сообщение: ≈60% отводится на список путей, ≈40% — на содержимое скелета. Обрезанное содержимое помечается как «available on demand»; если усекается даже список путей, добавляется счётчик скрытых файлов с подсказкой найти их через `repo_search`. Модель никогда не делает вывод, что файла не существует (закреплено правилом №10 системного промпта).
4. **Инструмент `repo_search`**: модель emit-ит fenced-блок ` ```repo_search ` с JSON (`query`, `glob`/`paths`, `max_results`); фронтенд исполняет серверный поиск по содержимому `GET /api/v1/coder/search` (regex с fallback на literal, сниппеты ±2 строки с номерами строк, до 50 результатов) и возвращает результат в тот же агентный ход (до 3 поисков за ход; промежуточные tool-call пузыри из UI убираются). Фильтры на сервере: только кодовые расширения, пропуск `node_modules/`, `.git/`, `dist/`, `build/`, `vendor/` и т.п., скачивание до 600 кандидатов.

### 12.4. Защита от prompt injection

Содержимое файлов из GitHub должно считаться недоверенными данными. Система должна:

- экранировать/разделять пользовательский инструктаж и содержимое репозитория;
- не позволять содержимому файла менять системные инструкции;
- не выполнять команды, содержащиеся в файлах, автоматически;
- требовать подтверждения пользователя перед любым экспортом.

## 13. Безопасность

### 13.1. Принципы

1. Least privilege — минимально необходимые права.
2. Deny by default — запрет по умолчанию для опасных путей и операций.
3. User confirmation — подтверждение любой записи в GitHub.
4. Server-side secrets — все токены только на сервере.
5. Auditability — все значимые действия логируются.
6. Fail closed — при ошибке валидации или отсутствии прав экспорт запрещён.

### 13.2. Требования к токенам

- не передавать токены во фронтенд;
- не логировать токены;
- не включать токены в сообщения об ошибках;
- шифровать при хранении;
-支持 ротацию ключа шифрования;
- при отзыве подключения удалять или cryptographically erase токен, насколько позволяет хранилище.

### 13.3. Защита путей

Запретить:

- абсолютные пути;
- пути с `..`;
- пути, начинающиеся с `/`;
- Windows drive letters, если не поддерживается явно;
- пути внутри `.git/`;
- symbolic links, если GitHub API возвращает такие объекты и это не разрешено политикой;
- пути, указанные в admin blacklist.

Пример blacklist:

```text
.git/*
.github/workflows/* # по умолчанию предупреждение, запись только с подтверждением администратора
.env
*.pem
*.key
secrets/*
```

Политика должна быть настраиваемой.

### 13.4. Ограничения размеров

Рекомендуемые значения по умолчанию:

- максимальный размер одного текстового файла: 1 MiB;
- максимальный суммарный размер изменений: 5 MiB;
- максимальное количество файлов в одном экспорте: 50;
- максимальная глубина дерева для отображения: настраиваемая.

Значения должны быть конфигурируемыми администратором.

### 13.5. Secret scanning

При включённой функции система должна проверять содержимое Change Set на признаки секретов:

- AWS access key;
- private keys;
- GitHub tokens;
- Slack tokens;
- JWT;
- passwords в явном виде;
- entropy-based detection.

Режимы:

- `warn` — показать предупреждение, разрешить экспорт после подтверждения;
- `block` — запретить экспорт;
- `off` — отключено.

По умолчанию для production рекомендуется `warn` или `block` для критичных паттернов.

### 13.6. CSRF и state

- OAuth callback обязан проверять `state`.
- Все изменяющие запросы должны быть защищены от CSRF в соответствии с механизмами Open WebUI.
- Использовать SameSite cookies и/или токены сессии, если применимо.

### 13.7. Authorization

Проверять на каждом запросе:

- пользователь аутентифицирован;
- функция Coder включена;
- подключение GitHub принадлежит текущему пользователю;
- пользователь имеет доступ к репозиторию через GitHub;
- операция разрешена политикой администратора.

### 13.8. XSS и безопасность отображения кода

- содержимое файлов и ответы модели должны экранироваться;
- markdown-рендеринг должен быть безопасным;
- code blocks не должны выполнять HTML/JS;
- ссылки из GitHub должны проверяться на допустимые hosts.

## 17. Критерии приёмки

Раздел считается принятым при выполнении всех обязательных критериев.

### AC-01. Доступность раздела

**Дано:** администратор включил Coder, пользователь аутентифицирован.  
**Когда:** пользователь открывает Open WebUI.  
**Тогда:** пользователь видит вход в раздел Coder или согласованный эквивалентный доступ.

### AC-02. Отключение раздела

**Дано:** администратор отключил Coder.  
**Когда:** пользователь пытается открыть раздел или API.  
**Тогда:** доступ запрещён с понятным сообщением.

### AC-03. Подключение GitHub

**Дано:** пользователь не подключил GitHub.  
**Когда:** пользователь запускает подключение и завершает授权 на GitHub.  
**Тогда:** backend сохраняет зашифрованный токен, UI отображает подключённый аккаунт, токен не виден клиенту.

### AC-04. Отзыв подключения

**Дано:** GitHub подключён.  
**Когда:** пользователь нажимает «Отключить».  
**Тогда:** локальный доступ удалён/помечён неактивным, повторный экспорт без нового подключения невозможен.

### AC-05. Выбор репозитория

**Дано:** пользователь подключил GitHub.  
**Когда:** пользователь открывает селектор репозиториев.  
**Тогда:** отображаются доступные репозитории, включая приватные, если права предоставлены.

### AC-06. Просмотр файлов

**Дано:** выбран репозиторий и ветка.  
**Когда:** пользователь выбирает файл.  
**Тогда:** система отображает содержимое файла или понятную ошибку, если файл слишком большой/бинарный/недоступен.

### AC-07. Генерация Change Set

**Дано:** пользователь запросил изменение кода.  
**Когда:** модель вернула валидный Change Set.  
**Тогда:** UI отображает список файлов, операцию, объяснение и кнопку предпросмотра diff.

### AC-08. Валидация опасных путей

**Дано:** Change Set содержит путь с `..`, абсолютный путь или запрещённый путь.  
**Когда:** система валидирует изменения.  
**Тогда:** экспорт блокируется, пользователю показана ошибка.

### AC-09. Предпросмотр diff

**Дано:** Change Set валиден.  
**Когда:** пользователь открывает предпросмотр.  
**Тогда:** система показывает diff по каждому файлу без выполнения записи в GitHub.

### AC-10. Экспорт в новую ветку

**Дано:** пользователь подтвердил экспорт, выбрал новую ветку.  
**Когда:** backend выполняет экспорт.  
**Тогда:** в GitHub создаётся ветка, коммит с указанными изменениями, UI показывает ссылку на коммит.

### AC-11. Создание Pull Request

**Дано:** пользователь включил опцию PR.  
**Когда:** экспорт выполнен успешно.  
**Тогда:** создан PR из новой ветки в базовую, UI показывает ссылку на PR.

### AC-12. Защита от дублирования

**Дано:** пользователь повторно отправляет тот же export с тем же idempotency key.  
**Когда:** первая задача уже выполнена успешно.  
**Тогда:** система не создаёт новый коммит/PR, а возвращает результат существующей задачи.

### AC-13. Обработка protected branch

**Дано:** базовая ветка защищена.  
**Когда:** пользователь пытается выполнить прямой commit в неё.  
**Тогда:** система запрещает это действие и предлагает создать новую ветку/PR.

### AC-14. Аудит

**Дано:** выполнено подключение, просмотр, валидация или экспорт.  
**Когда:** событие произошло.  
**Тогда:** в audit log записано событие без секретов, с пользователем, временем, target и correlation ID.

### AC-15. Отсутствие утечек токенов

**Дано:** выполнены все основные сценарии.  
**Когда:** проверены логи, network responses, БД в открытом виде для обычного пользователя, сообщения ошибок.  
**Тогда:** токены GitHub не обнаружены.

### AC-16. Тесты

**Дано:** код готов к приёмке.  
**Когда:** запущены unit/integration/E2E tests.  
**Тогда:** все критические тесты проходят, покрытие бизнес-логики не ниже согласованного уровня.

## 18. Риски и меры снижения

| Риск | Вероятность | Влияние | Меры снижения |
|---|---:|---:|---|
| Open WebUI не позволяет нативно добавить раздел | Средняя | Высокое | Этап 0, ADR, fallback через Function/preset, согласование UX |
| Утечка GitHub токена | Низкая | Критическое | Server-only storage, encryption, masking, security review |
| Ошибочная запись в production-репозиторий | Средняя | Высокое | Обязательное подтверждение, protected branch policy, default new branch, PR mode |
| Prompt injection через содержимое репозитория | Средняя | Высокое | Недоверенный контекст, разделение инструкций, запрет автодействий |
| Превышение лимитов GitHub API | Средняя | Среднее | Кеширование, throttling, retry с backoff, async jobs |
| Большие репозитории замедляют UI | Средняя | Среднее | Ленивая загрузка дерева, пагинация, ограничение глубины |
| Модель возвращает невалидный JSON | Высокая | Среднее | Строгая схема, repair loop, понятные ошибки |
| Конфликт базовой ветки во время экспорта | Средняя | Среднее | Preview, повторная проверка перед записью, ideal branch creation |
| Секреты попадают в код | Средняя | Высокое | Secret scanning, блокировка/предупреждение, обучение пользователей |
| Сложность сопровождения форка Open WebUI | Средняя | Высокое | Максимальное использование штатных扩展, модульность, документация |

## 24. Пример успешного пользовательского потока

1. Пользователь открывает **Coder**.
2. Система показывает: «GitHub не подключён».
3. Пользователь нажимает **Подключить GitHub** и завершает авторизацию.
4. Пользователь выбирает репозиторий `acme/backend` и ветку `main`.
5. Пользователь прикрепляет файл `src/api/users.py`.
6. В чате пишет: «Добавь валидацию email и напиши тесты».
7. Модель возвращает ответ и Change Set:
   - update `src/api/users.py`;
   - create `tests/test_users_email.py`.
8. Пользователь нажимает **Предпросмотр изменений**.
9. Система показывает diff и предупреждений нет.
10. Пользователь нажимает **Экспортировать в GitHub**.
11. Указывает ветку `coder/email-validation`, сообщение коммита, включает PR.
12. Система создаёт branch, commit, PR.
13. UI показывает:
    - коммит: `https://github.com/acme/backend/commit/...`
    - PR: `https://github.com/acme/backend/pull/123`
14. Событие записано в аудит.
