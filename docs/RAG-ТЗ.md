# ТЕХНИЧЕСКОЕ ЗАДАНИЕ  
## на разработку системы динамической композиции RAG-стратегий для адаптивного ответа на пользовательские запросы

**Дата подготовки:** 28.09.2026  
**Наименование системы:** Автоматизированная информационная система «Адаптивный RAG-оркестратор» далее — **Система**  
**Тип документа:** техническое задание на проектирование, разработку, тестирование и внедрение

## 1. Общие положения

### 1.1. Назначение документа

Настоящее техническое задание определяет требования к разработке Системы, реализующей динамическую композицию различных RAG-стратегий (Retrieval-Augmented Generation) в зависимости от характера пользовательского запроса, контекста диалога, доступных источников данных, политик безопасности, ограничений по стоимости и времени ответа.

Документ распространяется на:

- архитектуру Системы;
- функциональные компоненты;
- алгоритмы маршрутизации и планирования выполнения;
- процессы извлечения, проверки и синтеза ответов;
- требования к данным, индексам, графу знаний и внешним инструментам;
- требования к безопасности, наблюдаемости, тестированию и эксплуатации;
- критерии приёмки.

### 1.2. Цель создания Системы

Целью создания Системы является разработка адаптивной платформы интеллектуального поиска и генерации ответов, способной:

1. Анализировать пользовательский запрос и определять его тип, сложность, доменную принадлежность, степень неоднозначности и требования к доказательной базе.
2. Динамически выбирать минимально достаточную комбинацию RAG-стратегий, а не выполнять все доступные пайплайны indiscriminately.
3. Обеспечивать генерацию ответов с подтверждением источниками, контролем галлюцинаций, проверкой согласованности и соблюдением политик безопасности.
4. Поддерживать расширяемую архитектуру, допускающую подключение новых источников данных, моделей, индексов, графовых структур и инструментов.
5. Обеспечивать наблюдаемость, воспроизводимость и возможность непрерывного улучшения качества за счёт сбора обратной связи и метрик.

### 1.3. Задачи Системы

Система должна решать следующие задачи:

- приём и предобработка пользовательских запросов;
- понимание запроса и контекста диалога;
- маршрутизация запроса между стратегиями обработки;
- построение плана выполнения на основе политики оркестрации;
- параллельное или последовательное выполнение одного или нескольких RAG-пайплайнов;
- сбор кандидатов ответа в единый пул;
- оценка кандидатов по релевантности, обоснованности, цитируемости, безопасности и согласованности;
- синтез финального ответа, уточняющего вопроса, отказа или сообщения о недостаточной уверенности;
- логирование, трассировка, метрики и аудит всех этапов обработки;
- поддержка многопользовательского режима, разграничения доступа и изоляции данных;
- поддержка обновления знаний, переиндексации, версионирования источников и моделей.

### 1.4. Область применения

Система предназначена для использования в качестве интеллектуального ассистента по работе с корпоративными, научными, техническими, юридическими, финансовыми или иными документированными данными, а также, при наличии соответствующих политик, внешними веб-источниками и API.

Типовые сценарии применения:

-问答 по внутренней документации;
- поиск по базе знаний;
- анализ технических регламентов;
- поддержка клиентов;
- исследовательские ассистенты;
- сравнительный анализ документов;
- ответы на многошаговые вопросы;
- выявление связей между сущностями;
- подготовка аналитических справок с указанием источников.

### 1.5. Термины и определения

| Термин | Определение |
|---|---|
| RAG | Архитектура генерации ответов Large Language Model с предварительным извлечением релевантных данных из внешних источников. |
| Native RAG | Классический RAG-пайплайн на основе векторного, keyword или hybrid search по фрагментам документов. |
| Graph RAG | RAG-стратегия, использующая граф знаний, графовые связи, общности сущностей или структурные обходы для формирования контекста. |
| Agentic RAG | Стратегия, в которой модель или агент выполняет многошаговое планирование, вызывает инструменты, проверяет промежуточные результаты и формирует ответ. |
| Hybrid RAG | Комбинированный пайплайн, объединяющий несколько механизмов извлечения до этапа генерации. |
| Web/API Tool Pipeline | Пайплайн, использующий внешние веб-источники, API, базы данных или вычислительные инструменты. |
| Оркестратор | Компонент, принимающий решение о выборе, порядке и параметрах выполнения стратегий обработки. |
| Execution Planner | Подкомпонент оркестратора, формирующий план выполнения в виде DAG или последовательности задач. |
| Candidate Response | Промежуточный ответ, сформированный одним из пайплайнов. |
| Groundedness | Степень, в которой утверждения ответа подтверждаются извлечёнными источниками. |
| Citation Verification | Проверка корректности ссылок на источники и их соответствия утверждениям. |
| Trace | Совокупность данных о прохождении запроса через компоненты Системы. |
| Policy Engine | Модуль применения бизнес-правил, ограничений безопасности, стоимостных и временных бюджетов. |

### 1.6. Обозначения обязательности требований

В настоящем документе используются следующие модальные обозначения:

- **должен** — обязательное требование;
- **следует** — рекомендуемое требование, отступление от которого должно быть обосновано;
- **может** — необязательная возможность;
- **не должен** — прямой запрет.

## 2. Общие требования к Системе

### 2.1. Принцип динамической композиции

Система должна реализовывать принцип динамической композиции RAG-стратегий. Это означает, что для каждого запроса должен формироваться индивидуальный план обработки, включающий одну или несколько стратегий, выбранных на основе:

- типа запроса;
- сложности;
- домена;
- требуемого уровня доказательности;
- наличия графовых связей;
- необходимости внешних инструментов;
- степени неоднозначности;
- ограничений по latencies и стоимости;
- политик безопасности и доступа;
- исторической эффективности маршрутов для аналогичных запросов.

Система **не должна** по умолчанию запускать все доступные пайплайны для каждого запроса. Запуск нескольких стратегий допускается только при наличии обоснования, например:

- низкая уверенность первичного маршрута;
- противоречивые источники;
- высокий риск ошибки;
- запрос относится к критичной области;
- пользователь или бизнес-процесс требует расширенной проверки.

### 2.2. Принцип минимально достаточной обработки

Система должна стремиться к выбору минимально достаточного набора компонентов, обеспечивающего приемлемое качество ответа. Предпочтительная эскалация сложности должна происходить по нарастающей:

1. прямой ответ или кэш;
2. Native RAG;
3. Hybrid RAG;
4. Graph RAG;
5. Agentic RAG;
6. полный ансамбль с проверкой и синтезом.

### 2.3. Принцип проверяемости ответа

Любой факт, содержащийся в финальном ответе, должен быть прослеживаем до источника или явно помечен как:

- гипотеза;
- вывод модели;
- недостаточность данных;
- противоречие источников;
- внешний непроверенный источник.

Система не должна представлять непроверенные утверждения как достоверные факты.

### 2.4. Принцип безопасности по умолчанию

Все компоненты Системы должны проектироваться с учётом модели zero trust. Доступ к данным должен предоставляться только после проверки полномочий пользователя, контекста запроса и политиков tenant/organization/document-level access.

### 2.5. Принцип наблюдаемости

Каждый запрос должен иметь уникальный идентификатор трассировки. Система должна сохранять достаточно информации для восстановления цепочки:

запрос → анализ → маршрутизация → план → пайплайны → кандидаты → оценка → синтез → ответ.

## 3. Целевая архитектура

### 3.1. Общая схема

Целевая архитектура Системы имеет следующий вид:

```text
User Query
    |
    v
Preprocessing Layer
    |
    v
Router / Orchestrator
    |
    +-- Policy Engine
    |
    +-- Query Understanding
    |
    +-- Confidence Estimation
    |
    v
Execution Planner
    |
    +-- Native RAG Pipeline
    +-- Graph RAG Pipeline
    +-- Agentic RAG Pipeline
    +-- Hybrid RAG Pipeline
    +-- Web/API Tool Pipeline
    |
    v
Candidate Response Pool
    |
    v
Response Evaluation Layer
    |
    +-- Relevance Scoring
    +-- Groundedness Check
    +-- Contradiction Detection
    +-- Citation Verification
    +-- Safety Filter
    |
    v
Response Synthesis Layer
    |
    +-- Select best answer
    +-- Merge answers
    +-- Ask clarification
    +-- Return uncertainty
    |
    v
Final User Response
```

### 3.2. Логические слои архитектуры

Система должна быть разделена на следующие логические слои:

1. **Presentation Layer**  
   Пользовательский интерфейс, API-шлюз, каналы ввода-вывода.

2. **Orchestration Layer**  
   Предобработка, понимание запроса, политика, маршрутизация, планирование выполнения.

3. **Execution Layer**  
   RAG-пайплайны, графовые модули, агентные модули, инструменты, внешние API.

4. **Evaluation Layer**  
   Проверка качества, обоснованности, цитируемости, безопасности и согласованности.

5. **Synthesis Layer**  
   Формирование финального ответа, уточнений, отказов или сообщений о неопределённости.

6. **Data & Knowledge Layer**  
   Хранилища документов, векторные индексы, keyword-индексы, графы знаний, метаданные, ACL, кэши.

7. **Observability & Governance Layer**  
   Логи, метрики, трейсы, аудит, управление моделями, политиками, версиями и оценками качества.

## 4. Функциональные требования

## 4.1. Preprocessing Layer

### 4.1.1. Назначение

Слой предобработки должен подготавливать входной запрос к дальнейшему анализу и маршрутизации.

### 4.1.2. Обязательные функции

Слой предобработки **должен**:

1. Принимать запрос от пользователя или вызывающей системы.
2. Извлекать текст запроса, вложения, идентификатор сессии, историю диалога, метаданные пользователя и приложения.
3. Нормализовать текст:
   - удаление служебных символов;
   - приведение регистра там, где это уместно;
   - унификация пробелов;
   - обработка переносов строк;
   - удаление невалидных Unicode-последовательностей.
4. Определять язык запроса.
5. Выявлять потенциально чувствительные данные:
   - персональные данные;
   - секреты;
   - токены;
   - медицинские, финансовые или юридические категории, если заданы политики.
6. Выполнять первичную проверку безопасности:
   - prompt injection;
   - jailbreak-паттерны;
   - попытки обхода ограничений;
   - запросы на раскрытие системных инструкций;
   - запросы на выполнение недопустимых действий.
7. Извлекать базовые признаки запроса:
   - длину;
   - наличие вопросов;
   - наличие отрицаний;
   - наличие временных выражений;
   - наличие числовых значений;
   - наличие имён собственных;
   - наличие ссылочных выражений, например «это», «он», «вышеуказанный».
8. Разрешать местоимения и анафорические ссылки с использованием истории диалога.
9. Формировать объект `QueryContext`, передаваемый далее.
10. Проверять кэш идентичных или семантически близких запросов, если это разрешено политиками.
11. Ограничивать максимальный размер входного контекста в токенах.
12. Добавлять идентификатор запроса `request_id` и идентификатор трассировки `trace_id`.

### 4.1.3. Рекомендуемые функции

Слой предобработки **следует**:

- выявлять доменные термины;
- распознавать сущности;
- определять временну́ю привязку;
- классифицировать запрос по предварительным эвристикам;
- помечать запросы, требующие актуальных данных;
- отделять инструктивную часть от вопросительной.

### 4.1.4. Выход слоя

Результатом работы слоя предобработки должен быть объект `QueryContext`, включающий как минимум:

```json
{
  "request_id": "uuid",
  "trace_id": "uuid",
  "timestamp": "ISO-8601",
  "raw_query": "string",
  "normalized_query": "string",
  "language": "ru|en|...",
  "session_id": "string|null",
  "conversation_history": [],
  "user_context": {
    "user_id": "string",
    "tenant_id": "string",
    "roles": [],
    "permissions": []
  },
  "attachments": [],
  "detected_entities": [],
  "pii_flags": [],
  "safety_flags": [],
  "cache_key": "string|null",
  "token_count": 0
}
```

## 4.2. Router / Orchestrator

### 4.2.1. Назначение

Оркестратор является центральным компонентом Системы. Он должен принимать решение о том, какие пайплайны запускать, в каком порядке, с какими параметрами и при каких ограничениях.

Оркестратор должен включать следующие подкомпоненты:

- Policy Engine;
- Query Understanding;
- Confidence Estimation;
- Execution Planner.

### 4.2.2. Policy Engine

#### Обязательные функции

Policy Engine **должен**:

1. Хранить и применять политики:
   - доступа к данным;
   - допустимых пайплайнов;
   - допустимых инструментов;
   - лимитов стоимости;
   - лимитов времени;
   - требований к цитированию;
   - требований к безопасности;
   - требований к языку ответа;
   - требований к хранению логов.
2. Учитывать роль пользователя, tenant, приложение, канал и тип запроса.
3. Определять, какие источники разрешены для данного пользователя.
4. Определять, допустимо ли использование внешних веб-источников.
5. Определять, допустимо ли использование Agentic RAG и каких инструментов.
6. Устанавливать максимальное число шагов агента.
7. Устанавливать максимальное число кандидатов.
8. Устанавливать бюджеты:
   - `max_latency_ms`;
   - `max_cost_units`;
   - `max_tokens_input`;
   - `max_tokens_output`;
   - `max_tool_calls`.
9. Применять правила эскалации и fallback.
10. Блокировать выполнение запросов, нарушающих политики.
11. Формировать объект `PolicyDecision`.

#### Рекомендуемые функции

Policy Engine **следует**:

- поддерживать конфигурацию политик как код;
- версионировать политики;
-允许 A/B-тестирование политик;
- поддерживать динамическое обновление без перезапуска Системы;
- учитывать бизнес-критичность запроса.

#### Выход

```json
{
  "policy_id": "string",
  "allowed_pipelines": [],
  "allowed_tools": [],
  "allowed_sources": [],
  "max_latency_ms": 0,
  "max_cost_units": 0,
  "required_citations": true,
  "safety_level": "low|medium|high|critical",
  "escalation_allowed": true,
  "fallback_policy": "string"
}
```

### 4.2.3. Query Understanding

#### Назначение

Модуль понимания запроса должен определять семантические и прагматические характеристики запроса, необходимые для маршрутизации.

#### Обязательные функции

Query Understanding **должен**:

1. Классифицировать запрос по типу намерения:
   - `simple_fact`;
   - `definition`;
   - `procedural`;
   - `comparative`;
   - `causal`;
   - `temporal`;
   - `multi_hop`;
   - `graph_relation`;
   - `summary`;
   - `analysis`;
   - `calculation`;
   - `external_lookup`;
   - `ambiguous`;
   - `unsupported`;
   - `unsafe`;
   - `conversational`.
2. Определять сложность запроса:
   - low;
   - medium;
   - high;
   - very_high.
3. Определять доменную область, если задан список доменов.
4. Выявлять необходимость:
   - точного совпадения терминов;
   - семантического поиска;
   - графового обхода;
   - внешних данных;
   - вычислений;
   - сравнения нескольких источников;
   - многошагового рассуждения.
5. Оценивать степень неоднозначности.
6. Определять, требуется ли уточняющий вопрос.
7. Извлекать ключевые сущности и отношения.
8. Формировать гипотезы о необходимых типах доказательств.
9. Учитывать историю диалога.
10. Возвращать置信度 по каждому классу или признаку.

#### Рекомендуемые функции

Query Understanding **следует**:

- использовать лёгкую модель или эвристики для первичной классификации;
- использовать LLM только при необходимости;
- поддерживать обучение на реальных запросах;
- хранить калибровочные метрики точности классификатора;
- выявлять drift распределения запросов.

#### Выход

```json
{
  "intent": "string",
  "domain": "string|null",
  "complexity": "low|medium|high|very_high",
  "requires_graph": false,
  "requires_multi_step": false,
  "requires_external_data": false,
  "requires_calculation": false,
  "ambiguity_score": 0.0,
  "answerability_score": 0.0,
  "safety_risk_score": 0.0,
  "entities": [],
  "relations": [],
  "temporal_expressions": [],
  "confidence": 0.0,
  "recommended_pipelines": []
}
```

### 4.2.4. Confidence Estimation

#### Назначение

Модуль оценки уверенности должен определять, насколько вероятно, что выбранный маршрут или набор маршрутов даст приемлемый ответ.

#### Обязательные функции

Confidence Estimation **должен**:

1. Оценивать уверенность на основе:
   - результатов Query Understanding;
   - исторической статистики по аналогичным запросам;
   - доступности источников;
   - качества индексов;
   - свежести данных;
   - полноты покрытия запроса;
   - предыдущих попыток обработки;
   - отзывов пользователей.
2. Формировать итоговый `routing_confidence`.
3. Определять режим обработки:
   - `fast_path`;
   - `standard`;
   - `deep`;
   - `ensemble`;
   - `clarification_required`;
   - `refusal_recommended`.
4. Передавать результат в Execution Planner.
5. Поддерживать калибровку: заявленная уверенность должна коррелировать с фактическим качеством ответа.

#### Рекомендуемые пороги

Если иное не установлено политиками, рекомендуется использовать следующие ориентиры:

| Диапазон уверенности | Действие |
|---|---|
| ≥ 0.85 | Один оптимальный пайплайн |
| 0.65–0.84 | Два взаимодополняющих пайплайна |
| 0.45–0.64 | Эскалация или гибридный ансамбль |
| < 0.45 | Уточняющий вопрос, отказ или глубокая проверка |

Эти значения должны быть конфигурируемыми.

#### Выход

```json
{
  "routing_confidence": 0.0,
  "estimated_success_probability": 0.0,
  "estimated_latency_ms": 0,
  "estimated_cost_units": 0,
  "recommended_mode": "fast_path|standard|deep|ensemble|clarify|refuse",
  "reason_codes": []
}
```

---

### 4.2.5. Execution Planner

#### Назначение

Execution Planner должен преобразовать решение оркестратора в исполняемый план обработки запроса.

#### Обязательные функции

Execution Planner **должен**:

1. Формировать план в виде DAG или упорядоченной последовательности задач.
2. Указывать для каждой задачи:
   - тип пайплайна;
   - входные параметры;
   - таймаут;
   - число повторных попыток;
   - приоритет;
   - бюджет токенов;
   - бюджет стоимости;
   - зависимость от других задач;
   - условия запуска;
   - условия отмены.
3. Поддерживать режимы:
   - последовательное выполнение;
   - параллельное выполнение;
   - условное выполнение;
   - эскалация по результату;
   - досрочное завершение при достижении достаточного качества.
4. Учитывать политики Policy Engine.
5. Ограничивать общее время обработки.
6. Ограничивать совокупную стоимость.
7. Предусматривать fallback при:
   - таймауте;
   - ошибке модели;
   - недоступности индекса;
   - отсутствии графа;
   - отказе инструмента;
   - низком качестве retrieval;
   - нарушении safety-фильтра.
8. Формировать объект `ExecutionPlan`.
9. Передавать план в исполнительный слой.
10. Логировать причину выбора каждого узла плана.

#### Обязательные режимы планирования

Система должна поддерживать следующие режимы:

##### Режим 1: Single-route

```text
Query -> один пайплайн -> кандидат -> оценка -> ответ
```

Применяется при высокой уверенности и простоте запроса.

##### Режим 2: Parallel ensemble

```text
Query -> несколько пайплайнов одновременно -> пул кандидатов -> оценка -> синтез
```

Применяется при среднем риске, необходимости перекрёстной проверки или недостаточной уверенности одного маршрута.

##### Режим 3: Sequential escalation

```text
Query -> дешёвый пайплайн -> проверка недостаточности -> более сложный пайплайн -> ответ
```

Применяется для экономии ресурсов.

##### Режим 4: Conditional hybrid

```text
Query -> Native RAG + Graph-assisted retrieval -> единый контекст -> генерация
```

Применяется, когда граф используется не как отдельный ответ, а как обогащение retrieval.

##### Режим 5: Agentic workflow

```text
Query -> планирование -> tool calls -> reflection -> проверка -> ответ
```

Применяется для многошаговых задач, расчётов, внешних данных и сложных сравнений.

##### Режим 6: Clarification mode

```text
Query -> обнаружение неоднозначности -> уточняющий вопрос -> ожидание ответа пользователя
```

##### Режим 7: Refusal mode

```text
Query -> нарушение политики или недопустимость -> безопасный отказ
```

#### Выход

```json
{
  "plan_id": "uuid",
  "mode": "single|parallel|sequential|conditional|agentic|clarify|refuse",
  "tasks": [
    {
      "task_id": "uuid",
      "pipeline": "native_rag|graph_rag|agentic_rag|hybrid_rag|tool_pipeline",
      "depends_on": [],
      "timeout_ms": 0,
      "retry_policy": {},
      "budget": {},
      "parameters": {},
      "condition": "string|null"
    }
  ],
  "global_timeout_ms": 0,
  "global_budget": {},
  "fallback_plan": []
}
```

## 4.3. Исполнительные пайплайны

Система должна поддерживать модульную архитектуру пайплайнов. Каждый пайплайн должен реализовывать единый интерфейс входа и выхода, но иметь собственную внутреннюю логику.

### 4.3.1. Общий контракт пайплайна

Каждый пайплайн **должен**:

1. Принимать:
   - `QueryContext`;
   - `PolicyDecision`;
   - `TaskParameters`;
   - `TraceContext`.
2. Возвращать:
   - `CandidateResponse`;
   - список использованных источников;
   - метрики выполнения;
   - статус успеха или ошибки.
3. Соблюдать таймаут и бюджет.
4. Не выходить за разрешённые источники и инструменты.
5. Передавать provenance-информацию для каждого фрагмента контекста.
6. Логировать этапы retrieval, reranking, generation и tool usage.
7. Поддерживать отмену выполнения при превышении глобального лимита.

---

### 4.3.2. Native RAG Pipeline

#### Назначение

Native RAG предназначен для быстрого извлечения релевантных фрагментов документов и генерации ответа на их основе.

#### Обязательные функции

Native RAG Pipeline **должен**:

1. Выполнять retrieval по:
   - векторному индексу;
   - keyword-индексу;
   - hybrid-индексу, если настроен.
2. Применять фильтры по метаданным:
   - tenant;
   - role;
   - document class;
   - дата;
   - язык;
   - статус документа;
   - доступность.
3. Выполнять reranking найденных фрагментов.
4. Формировать контекст с указанием:
   - document_id;
   - chunk_id;
   - offset;
   - score;
   - source URI;
   - version.
5. Генерировать ответ с цитатами.
6. Ограничивать длину контекста.
7. Передавать в candidate все использованные source spans.
8. Поддерживать извлечение точных цитат, а не только парафраза.

#### Зона применимости

Native RAG следует использовать для:

- прямых фактических вопросов;
- поиска по документации;
- FAQ;
- вопросов, ответ на которые содержится в одном или нескольких фрагментах;
- задач с низкой и средней сложностью.

#### Ограничения

Native RAG не должен использоваться как единственный источник для:

- сложных многошаговых вопросов;
- вопросов о глобальных связях в корпусе;
- задач, требующих расчётов;
- задач, требующих актуальных внешних данных;
- вопросов с высокой неоднозначностью.

---

### 4.3.3. Graph RAG Pipeline

#### Назначение

Graph RAG предназначен для использования графовых структур знаний, связей между сущностями, общностей, иерархий и тематических кластеров.

#### Обязательные функции

Graph RAG Pipeline **должен**:

1. Использовать граф знаний или графовую индексацию документов.
2. Выполнять entity linking запроса к узлам графа.
3. Поддерживать:
   - обход соседей;
   - поиск путей между сущностями;
   - выявление общностей;
   - агрегацию по кластерам;
   - ранжирование узлов и рёбер;
   - фильтрацию по доступу.
4. Формировать структурный контекст:
   - сущности;
   - отношения;
   - свойства;
   - источники узлов и рёбер;
   - степени уверенности извлечения графа.
5. Генерировать ответ на основе графового контекста.
6. Явно указывать, какие утверждения основаны на графовых связях.
7. Не допускать вывода несуществующих связей.
8. Поддерживать объяснимость пути в графе.
9. Учитывать ACL на уровне узлов, рёбер, свойств и сообществ.
10. Передавать provenance для каждого элемента графа.

#### Зона применимости

Graph RAG следует использовать для:

- вопросов о связях между объектами;
- причинно-следственных анализ;
- иерархий;
- зависимостей;
- глобальных тем корпуса;
- выявления скрытых соотношений;
- доменов с сильной структурой связей.

#### Обязательное требование безопасности

Граф не должен раскрывать связи между документами, к которым пользователь не имеет доступа. Если связь проходит через запрещённый узел, Система должна либо скрыть её, либо вернуть обезличенное сообщение о недостаточности прав.

---

### 4.3.4. Agentic RAG Pipeline

#### Назначение

Agentic RAG предназначен для многошагового решения задач, требующих планирования, использования инструментов, проверки промежуточных результатов и корректировки стратегии.

#### Обязательные функции

Agentic RAG Pipeline **должен**:

1. Формировать план действий.
2. Выполнять ограниченное число шагов.
3. Вызывать разрешённые инструменты:
   - search;
   - SQL;
   - API;
   - calculator;
   - code execution;
   - document parser;
   - graph query;
   - web fetch.
4. Проверять результаты каждого шага.
5. Поддерживать reflection:
   - достаточно ли информации;
   - есть ли противоречия;
   - нужно ли уточнение;
   - нужно ли изменить стратегию.
6. Останавливаться при:
   - достижении цели;
   - исчерпании бюджета;
   - обнаружении недопустимого действия;
   - невозможности продолжить;
   - таймауте.
7. Не выполнять destructive actions без подтверждения, если это предусмотрено политикой.
8. Логировать все tool calls и их аргументы.
9. Передавать candidate с полной историей шагов.
10. Соблюдать sandbox-ограничения для выполнения кода и внешних вызовов.

#### Зона применимости

Agentic RAG следует использовать для:

- многошаговых исследований;
- сравнительного анализа;
- задач с расчётами;
- запросов, требующих нескольких источников;
- задач с динамическим выбором инструмента;
- случаев, когда один retrieval недостаточен.

#### Обязательные ограничения

Система **должна** ограничивать:

- максимальное число итераций;
- максимальное число вызовов инструментов;
- максимальный объём возвращаемых данных;
- время выполнения;
- стоимость;
- доступ к инструментам по ролям.

Agentic RAG не должен запускаться для простых фактических запросов, если это не оправдано политикой.

---

### 4.3.5. Hybrid RAG Pipeline

#### Назначение

Hybrid RAG объединяет несколько механизмов извлечения до этапа генерации, формируя единый обогащённый контекст.

#### Обязательные функции

Hybrid RAG Pipeline **должен**:

1. Комбинировать:
   - vector search;
   - keyword search;
   - graph retrieval;
   - metadata filtering;
   - reranking;
   - query expansion;
   - HyDE или аналогичные методы, если разрешено.
2. Устранять дублирование фрагментов.
3. Сохранять provenance каждого фрагмента.
4. Оценивать вклад каждого источника в итоговый контекст.
5. Формировать единый candidate response.
6. Поддерживать настраиваемые веса комбинации.

#### Зона применимости

Hybrid RAG следует использовать, когда:

- запрос требует и семантического, и точного совпадения;
- граф может дополнить векторный поиск;
- необходимо повысить recall без запуска полноценного ансамбля ответов.

---

### 4.3.6. Web/API Tool Pipeline

#### Назначение

Данный пайплайн обеспечивает доступ к внешним источникам, API, базам данных и сервисам.

#### Обязательные функции

Web/API Tool Pipeline **должен**:

1. Использовать только разрешённые источники и эндпоинты.
2. Проверять достоверность источника по заданным критериям:
   - официальный домен;
   - репутация;
   - дата публикации;
   - авторство;
   - наличие первичного источника.
3. Учитывать robots.txt, Terms of Service и правовые ограничения, если применимо.
4. Кэшировать внешние ответы с учётом TTL.
5. Отслеживать свежесть данных.
6. Передавать в candidate URL, snapshot, timestamp, hash содержимого.
7. Не раскрывать внутренние данные во внешних вызовах без разрешения.
8. Поддерживать подпись источников и уровень доверия.
9. Блокировать выполнение недоверенного JavaScript или активных элементов при извлечении веб-страниц.
10. Обрабатывать ошибки API, rate limits и недоступность.

#### Зона применимости

Следует использовать для:

- актуальных новостей;
- внешних справочников;
- биржевых данных;
- погодных данных;
- публичных API;
- задач, где внутренние знания недостаточны или устарели.

## 4.4. Candidate Response Pool

### 4.4.1. Назначение

Пул кандидатов отвечает за агрегацию промежуточных результатов, полученных различными пайплайнами.

### 4.4.2. Обязательные функции

Candidate Response Pool **должен**:

1. Хранить все кандидаты, полученные в рамках одного запроса.
2. Связывать каждый кандидат с:
   - пайплайном;
   - задачами плана;
   - источниками;
   - метриками;
   - trace_id.
3. Дедуплицировать идентичные или семантически близкие ответы.
4. Извлекать атомарные утверждения из кандидатов.
5. Сохранять исходные фрагменты для последующей проверки.
6. Не смешивать данные разных tenant.
7. Поддерживать TTL хранения кандидатов.
8. Передавать полный набор кандидатов в Response Evaluation Layer.

### 4.4.3. Структура кандидата

Каждый `CandidateResponse` **должен** содержать:

```json
{

  "pipeline": "string",
  "task_id": "uuid",
  "answer_text": "string",
  "claims": [
    {
      "claim_id": "uuid",
      "text": "string",
      "type": "fact|opinion|hypothesis|calculation|recommendation",
      "source_refs": []
    }
  ],
  "sources": [
    {
      "source_id": "string",
      "document_id": "string",
      "chunk_id": "string",
      "uri": "string",
      "title": "string",
      "snippet": "string",
      "offset_start": 0,
      "offset_end": 0,
      "score": 0.0,
      "version": "string",
      "hash": "string",
      "access_level": "string"
    }
  ],
  "metadata": {
    "latency_ms": 0,
    "cost_units": 0,
    "tokens_input": 0,
    "tokens_output": 0,
    "model_version": "string",
    "prompt_version": "string",
    "index_version": "string"
  },
  "self_confidence": 0.0,
  "status": "success|partial|failed",
  "error_code": "string|null"
}
```

## 4.5. Response Evaluation Layer

### 4.5.1. Назначение

Слой оценки должен определять качество кандидатов перед финальным синтезом.

### 4.5.2. Обязательные компоненты

Слой оценки **должен** включать:

- Relevance Scoring;
- Groundedness Check;
- Contradiction Detection;
- Citation Verification;
- Safety Filter.

Допускается расширение слоя другими метриками: freshness, authority, completeness, conciseness, readability, bias, policy compliance.

---

### 4.5.3. Relevance Scoring

#### Обязательные функции

Relevance Scoring **должен**:

1. Оценивать соответствие ответа исходному запросу.
2. Учитывать:
   - покрытие всех частей запроса;
   - отсутствие off-topic информации;
   - полноту;
   - лаконичность;
   - соответствие языку и стилю.
3. Возвращать числовую оценку и причины.
4. Поддерживать оценку на уровне утверждений, а не только всего ответа.

#### Выход

```json
{
  "relevance_score": 0.0,
  "coverage_score": 0.0,
  "conciseness_score": 0.0,
  "off_topic_penalty": 0.0,
  "reason_codes": []
}
```

---

### 4.5.4. Groundedness Check

#### Обязательные функции

Groundedness Check **должен**:

1. Разбивать ответ на атомарные утверждения.
2. Для каждого утверждения искать поддерживающие фрагменты в источниках.
3. Применять модель entailment или иной метод проверки поддержки.
4. Классифицировать утверждения:
   - supported;
   - partially_supported;
   - unsupported;
   - contradicted;
   - inferred;
   - external_unverified.
5. Помечать утверждения, не подтверждённые источниками.
6. Запрещать включение unsupported factual claims в финальный ответ без явной маркировки.
7. Учитывать различие между фактом, мнением, гипотезой и рекомендацией.

#### Обязательное правило

Любое фактическое утверждение в финальном ответе должно быть:

- подтверждено источником;
- или явно помечено как вывод модели;
- или удалено;
- или заменено формулировкой о недостатке данных.

---

### 4.5.5. Contradiction Detection

#### Обязательные функции

Contradiction Detection **должен**:

1. Сравнивать утверждения между:
   - кандидатами;
   - кандидатами и источниками;
   - разными фрагментами одного источника;
   - ответом и историей диалога.
2. Выявлять типы противоречий:
   - фактические;
   - числовые;
   - временные;
   - логические;
   - терминологические;
   - интерпретационные.
3. Оценивать серьёзность противоречия.
4. Передавать результат в Response Synthesis Layer.
5. Не разрешать синтез «сглаженного» ответа, скрывающего существенное противоречие.

#### Выход

```json
{
  "contradiction_found": true,
  "severity": "low|medium|high|critical",
  "pairs": [
    {
      "claim_a": "uuid",
      "claim_b": "uuid",
      "type": "numeric|temporal|factual|logical",
      "explanation": "string"
    }
  ]
}
```

---

### 4.5.6. Citation Verification

#### Обязательные функции

Citation Verification **должен**:

1. Проверять, что каждая ссылка соответствует реальному источнику.
2. Проверять, что цитируемый фрагмент поддерживает утверждение.
3. Проверять актуальность версии документа.
4. Проверять, что пользователь имеет право на просмотр источника.
5. Не допускать вымышленных document_id, URL, chunk_id или номеров страниц.
6. Формировать карту «утверждение → источник → фрагмент».
7. Поддерживать разные форматы цитирования:
   - inline citations;
   - footnote style;
   - source list;
   - clickable links.

#### Обязательное требование

Финальный ответ должен содержать метаданные цитирования, даже если пользовательский интерфейс отображает только видимые ссылки.

---

### 4.5.7. Safety Filter

#### Обязательные функции

Safety Filter **должен**:

1. Проверять ответ на:
   - вредоносные инструкции;
   - раскрытие секретов;
   - персональные данные;
   - конфиденциальную информацию;
   - дискриминационные высказывания;
   - незаконные действия;
   - медицинские, юридические или финансовые рекомендации сверх разрешённого уровня;
   - prompt leakage;
   - jailbreak success;
   - токсичность;
   - манипулятивные формулировки.
2. Применять политики tenant-specific safety rules.
3. Блокировать или модифицировать недопустимые фрагменты.
4. Формировать безопасное сообщение об отказе при необходимости.
5. Логировать срабатывания без сохранения запрещённого контента в открытом виде, если этого требуют политики.

## 4.6. Response Synthesis Layer

### 4.6.1. Назначение

Слой синтеза должен сформировать финальный ответ пользователю на основе кандидатов и отчёта оценки.

### 4.6.2. Обязательные действия

Response Synthesis Layer **должен** поддерживать следующие действия:

#### 1. Select best answer

Выбирать один кандидат, если:

- он имеет достаточную оценку;
- противоречия отсутствуют или несущественны;
- все факты подтверждены;
- safety-проверка пройдена.

#### 2. Merge answers

Объединять несколько кандидатов, если:

- они дополняют друг друга;
- нет неразрешимых противоречий;
- объединение повышает полноту;
- сохраняется цитируемость.

При объединении Система **не должна** создавать новые фактические утверждения, отсутствующие в источниках или подтверждённых выводах.

#### 3. Ask clarification

Формировать уточняющий вопрос, если:

- запрос неоднозначен;
- не хватает обязательных параметров;
- несколько интерпретаций равновероятны;
- ответ зависит от контекста, отсутствующего в запросе.

#### 4. Return uncertainty

Возвращать ответ с явной неопределённостью, если:

- источники противоречат друг другу;
- данных недостаточно для однозначного вывода;
- уверенность ниже порога, но частичный ответ возможен.

#### 5. Refuse

Отказывать, если:

- запрос нарушает политику безопасности;
- требуемые данные недоступны пользователю;
- ответ может причинить вред;
- отсутствует достаточное основание для ответа.

Отказ должен быть вежливым, понятным и, где возможно, предлагать легальную альтернативу.

### 4.6.3. Требования к финальному ответу

Финальный ответ **должен** включать:

- текст ответа;
- список источников или цитаты;
- уровень уверенности, если это предусмотрено UX;
- предупреждения о противоречиях или ограничениях, при наличии;
- идентификатор запроса для поддержки и аудита;
- метку о том, использованы ли внешние данные.

### 4.6.4. Формат финального ответа

```json
{
  "response_id": "uuid",
  "request_id": "uuid",
  "trace_id": "uuid",
  "answer_text": "string",
  "citations": [],
  "confidence": 0.0,
  "status": "answered|clarification|uncertain|refused|partial",
  "warnings": [],
  "used_pipelines": [],
  "sources_summary": [],
  "ui_hints": {}
}
```

## 5. Нефункциональные требования

## 5.1. Производительность

### 5.1.1. Целевые показатели задержки

Если иное не установлено SLA, рекомендуется установить следующие целевые показатели:

| Режим | p50 | p95 | p99 |
|---|---:|---:|---:|
| Fast path / cache hit | ≤ 300 мс | ≤ 800 мс | ≤ 1.5 с |
| Native RAG | ≤ 1.5 с | ≤ 3 с | ≤ 5 с |
| Hybrid / Graph-assisted | ≤ 2.5 с | ≤ 5 с | ≤ 8 с |
| Agentic RAG | ≤ 5 с | ≤ 12 с | ≤ 20 с |
| Full ensemble | ≤ 8 с | ≤ 15 с | ≤ 25 с |

Значения должны быть конфигурируемыми по tenant, типу запроса и приоритету.

### 5.1.2. Пропускная способность

Система должна поддерживать горизонтальное масштабирование и обрабатывать не менее `[N]` одновременных запросов, где `[N]` определяется эксплуатационными требованиями.

### 5.1.3. Бюджеты стоимости

Система должна учитывать стоимость:

- LLM-токенов;
- embedding-запросов;
- graph queries;
- tool calls;
- web fetch;
- storage и network.

Для каждого запроса должен рассчитываться `estimated_cost_units` и `actual_cost_units`.

---

## 5.2. Надёжность

Система **должна**:

1. Обрабатывать частичные отказы компонентов без полного падения сервиса.
2. Поддерживать retry с экспоненциальной задержкой.
3. Использовать circuit breaker для нестабильных зависимостей.
4. Поддерживать fallback на более простые пайплайны.
5. Гарантировать идемпотентность повторных запросов с тем же `idempotency_key`.
6. Сохранять состояние длинных агентных задач при перезапуске, если это предусмотрено режимом выполнения.
7. Иметь механизм graceful shutdown.
8. Поддерживать восстановление после сбоя индексов или графовых хранилищ.

Целевой уровень доступности: не менее **99.9%** для production-режима, если иное не установлено SLA.

---

## 5.3. Масштабируемость

Система **должна**:

- быть спроектированной как набор loosely coupled сервисов;
- поддерживать асинхронное выполнение через очереди или event bus;
-允许 независимое масштабирование retrieval, generation, evaluation и orchestration;
- поддерживать партиционирование индексов по tenant и домену;
- поддерживать кэширование:
  - запросов;
  - embedding;
  - retrieval результатов;
  - графовых подзапросов;
  - ответов инструментов;
  - финальных ответов при допустимой свежести.

---

## 5.4. Сопровождаемость

Система **должна**:

- иметь модульную архитектуру;
- поддерживать конфигурацию политик, маршрутов, моделей и промптов вне кода;
- версионировать:
  - модели;
  - промпты;
  - индексы;
  - графы;
  - политики;
  - evaluation datasets;
- поддерживать canary-развёртывание;
- поддерживать rollback;
- иметь документацию API и внутренних контрактов;
- поддерживать воспроизведение запроса по `trace_id`.

---

## 5.5. Воспроизводимость

Для каждого запроса Система **должна** сохранять достаточно данных, чтобы повторно воспроизвести обработку с учётом:

- версии модели;
- версии промпта;
- версии индекса;
- версии графа;
- версии политик;
- seed, если используется;
- temperature и иных параметров генерации;
- набора источников на момент запроса.

Полная детерминированность LLM не гарантируется, однако Система должна минимизировать неконтролируемую вариативность.

---

## 5.6. Локализация и языковая поддержка

Система **должна**:

- определять язык запроса;
- отвечать на языке запроса, если не задано иное;
- поддерживать многоязычный retrieval, если источники многоязычны;
- корректно обрабатывать транслитерацию и синонимы;
- поддерживать локализацию сообщений об ошибках и уточнениях.

Минимально требуемые языки определяются заказчиком. Для настоящего ТЗ по умолчанию: русский и английский.

## 6. Требования к безопасности

## 6.1. Аутентификация и авторизация

Система **должна** поддерживать:

- OAuth 2.0 / OpenID Connect;
- API keys для сервисных вызовов;
- mTLS для межсервисного взаимодействия, если применимо;
- RBAC и/или ABAC;
- проверку прав на уровне:
  - tenant;
  - пользователь;
  - роль;
  - документ;
  - фрагмент;
  - поле метаданных;
  - узел графа;
  - ребро графа;
  - инструмент;
  - внешний API.

## 6.2. Изоляция данных

Система **должна** guarantees:

- логическую изоляцию tenant;
- отсутствие утечек между клиентами;
- изоляцию кэшей по tenant и permission set;
- изоляцию логов и метрик, если это требуется политикой.

## 6.3. Защита от prompt injection

Система **должна**:

1. Отделять системные инструкции от пользовательского ввода.
2. Не позволять пользовательскому тексту изменять системные политики.
3. Санитизировать входные данные из документов и веб-страниц.
4. Рассматривать содержимое источников как данные, а не как команды.
5. Блокировать попытки:
   - раскрыть system prompt;
   - обойти ACL;
   - вызвать недопустимый инструмент;
   - изменить правила оценки;
   - получить скрытые данные.
6. Применять output filtering для обнаружения leakage.

## 6.4. Безопасность инструментов

Все инструменты **должны**:

- работать в sandbox;
- иметь whitelist операций;
- иметь лимиты ресурсов;
- не иметь доступа к секретам напрямую;
- требовать подтверждения для опасных действий;
- логировать все вызовы.

## 6.5. Защита персональных данных

При обработке персональных данных Система **должна** соответствовать применимому законодательству, включая, при необходимости, 152-ФЗ, GDPR и иные нормативные требования.

Требования:

- минимизация данных;
- шифрование при хранении и передаче;
- маскирование PII в логах;
- право на удаление;
- ограничение срока хранения;
- аудит доступа;
- согласие или иное правовое основание обработки.

## 6.6. Аудит

Система **должна** вести неизменяемый или защищённый от модификации журнал:

- кто запросил;
- что запрошено;
- какие источники использованы;
- какие политики применены;
- какие модели вызваны;
- какие инструменты использованы;
- какой ответ сформирован;
- какие нарушения обнаружены.

| Процедура | «как выполнить», шаги | Native RAG, Agentic RAG при необходимости |
| Сравнение | «чем отличается», «сравни» | Native + Graph/Hybrid, Agentic RAG |
| Причина/следствие | «почему», «влияет», «приводит к» | Graph RAG, Hybrid RAG |
| Многошаговый | несколько подвопросов | Agentic RAG, Native + Graph |
| Глобальный по корпусу | «основные темы», «общая картина» | Graph RAG, Hybrid RAG |
| Актуальный внешний | «сейчас», «сегодня», «новости» | Web/API Tool Pipeline |
| Расчёт | числа, формулы, агрегация | Agentic RAG с calculator/code |
| Неоднозначный | несколько интерпретаций | Clarification, затем выборочные пайплайны |
| Высокорисковый | медицина, право, финансы | Ensemble + evaluation + human review |
| Недостаточно данных | нет источников | Uncertainty или refusal |

## 10.2. Правила эскалации

Система **должна** эскалировать обработку, если:

1. Первый кандидат имеет `overall_score` ниже порога.
2. Groundedness ниже порога.
3. Обнаружено существенное противоречие.
4. Запрос требует данных, отсутствующих в первичном источнике.
5. Пользователь явно запрашивает подробный анализ.
6. Политика требует расширенной проверки для домена.
7. Confidence Estimation показал низкую уверенность.

Порядок эскалации по умолчанию:

```text
Native RAG
   ↓ недостаточность
Hybrid RAG / Graph-assisted retrieval
   ↓ недостаточность
Graph RAG или Agentic RAG
   ↓ высокий риск
Full ensemble + evaluation + synthesis
```

## 10.3. Правила деэскалации

Система **должна** прекращать дополнительные вызовы, если:

- получен кандидат с достаточной оценкой;
- достигнут бюджет;
- дальнейшие источники не добавляют новой информации;
- обнаружено, что запрос неустранимо неоднозначен и требуется уточнение;
- safety filter требует остановки.

## 10.4. Псевдокод логики оркестратора

```python
def orchestrate(query_context):
    pre = preprocess(query_context)

    if cache_hit(pre):
        return get_cached_response(pre)

    policy = policy_engine.evaluate(pre)
    if policy.deny:
        return safe_refusal(policy.reason)

    analysis = query_understanding.analyze(pre, policy)
    confidence = confidence_estimator.estimate(analysis, pre.history, policy)

    plan = execution_planner.build(
        analysis=analysis,
        policy=policy,
        confidence=confidence
    )

    candidates = execute_plan(plan)

    if insufficient(candidates, policy):
        escalation_plan = execution_planner.escalate(plan, candidates)
        candidates += execute_plan(escalation_plan)

    evaluation = response_evaluator.evaluate(candidates, pre, policy)

    if evaluation.clarification_required:
        return build_clarification(evaluation)

    if evaluation.refusal_required:
        return safe_refusal(evaluation.reason)

    if evaluation.uncertainty_high:
        return build_uncertain_answer(evaluation)

    if evaluation.contradiction_critical:
        return build_balanced_answer_with_warnings(evaluation)

    return synthesize_final_answer(evaluation)
```

## 18. Критерии приёмки

Система считается принятой при выполнении следующих условий:

### 18.1. Функциональные критерии

8. Обеспечено цитирование источников.
9. Реализовано разграничение доступа.
10. Реализованы логи, метрики и трассировка.

### 18.2. Нефункциональные критерии

1. Достигнуты согласованные SLA по latency и availability.

3. Пройдены security tests.
4. Пройдены load tests.
5. Пройдено регрессионное тестирование на golden set.
6. Подтверждены метрики качества из раздела 12.3 или согласованные заказчиком значения.

8. Проведено обучение персонала.

## 20. Итоговая формулировка требований

Система должна быть реализована не как статичный набор из трёх RAG-вариантов, а как **интеллектуальная адаптивная платформа оркестрации**, которая:

1. Понимает запрос.
2. Оценивает риск и сложность.
3. Применяет политики доступа, безопасности, стоимости и времени.
4. Строит минимально достаточный план выполнения.
5. Запускает Native RAG, Graph RAG, Agentic RAG, Hybrid RAG или Tool Pipeline только там, где это оправдано.
6. Собирает кандидатов.
7. Проверяет факты, цитаты, противоречия и безопасность.
8. Синтезирует финальный ответ или корректно сообщает о невозможности ответа.
9. Обеспечивает полную наблюдаемость и возможность улучшения.

Таким образом, ключевой архитектурной идеей является не «всегда запускать всё», а **динамическая композиция RAG-стратегий под конкретный запрос** с обязательным контролем качества, безопасности и стоимости.
