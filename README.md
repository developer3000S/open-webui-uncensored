## Ключевые возможности Open WebUI ⭐


- 🚀 **Простая настройка**: Устанавливайте без труда через pip, uv, Docker или Kubernetes (kubectl, kustomize или helm). Для контейнерных развертываний доступны образы с тегами `:ollama` и `:cuda`.

- 🤝 **Широкая интеграция моделей и API**: Подключайте любой OpenAI-совместимый API вместе с локальными моделями Ollama. Укажите URL API на **LMStudio, GroqCloud, Mistral, OpenRouter, vLLM и другие**, чтобы свободно комбинировать провайдеров.

- 🔐 **Тонкая RBAC и группы пользователей**: Администраторы задают роли, группы и права максимально детально, чтобы каждому пользователю был доступ ровно к тому, что нужно. По умолчанию — безопасно, а опыт настраивается под каждую группу.

- 🧩 **Поддержка плагинов**: Расширяйте Open WebUI с помощью **фильтров**, **действий**, **pipe**, **tools** и **skills**. Подключайте внешние сервисы через **MCP**, **MCPO** и **OpenAPI tool servers**. Стройте собственные интеграции, лимиты запросов, сценарии согласования, подключения данных и многое другое.

- 🤖 **Модели и агенты**: Оборачивайте любую базовую модель в пользовательские инструкции, tools и знания, чтобы создавать специализированных агентов. Поддерживаются динамические переменные, контроль доступа по пользователям/группам и импорт готовых пресетов через [Open WebUI Community](https://openwebui.com/).

- 📝 **Заметки**: Отдельное рабочее пространство для контента вне диалогов. Создавайте черновики в расширенном редакторе, используйте ИИ для перезаписи выбранного текста и прикрепляйте заметки к любому чату для полного контекстного внедрения.

- 📢 **Каналы**: Общие пространства в реальном времени, где ваша команда и ИИ-модели работают в одной временной шкале. Помечайте модели, чтобы они готовили или критиковали ответы, с ветками (threads), реакциями, закреплениями и контролем доступа.

- 🧠 **Устойчивая память**: ИИ запоминает факты о вас на протяжении диалогов, перенося контекст из одного чата в следующий.

- ✅ **Живой рабочий процесс и поток сообщений**: Наблюдайте, как ИИ строит ответ и проходит чек-листы в реальном времени. Ставьте сообщения в очередь, пока ИИ ещё отвечает — они отправятся автоматически, когда всё будет готово.

- 📅 **Календарь и планирование с ИИ**: Встроенные личные и общие календари с представлениями месяц/неделя/день, повторяющимися событиями, цветовой маркировкой, участниками и напоминаниями. Модели управляют вашим расписанием в диалоге через нативное function calling.

- ⏱️ **Автоматизации**: Планируйте подсказки (prompts) для выполнения по повторяющимся расписаниям. Запуски отображаются в календаре, а каждый завершённый запуск связывается обратно с чатом, который его сформировал.

- 💻 **Coder**: Собственное приложение для агентной работы с кодом GitHub-репозиториев. Открывается **в отдельном окне браузера** как самостоятельное приложение (основное боковое меню скрыто). Подключение через GitHub OAuth (токены хранятся только на сервере, AES-256-GCM). Две вкладки: **Workspace** (чат с кодовой моделью с кнопкой очистки чата, Change Set с unified diff, экспорт) и **Окружение (Environment)** — список подключённых GitHub-репозиториев; при клике на репозиторий он автоматически подгружается в рабочее пространство. Работает с репозиториями **любого размера**: модель всегда получает полное дерево файлов плюс компактный «скелет» из ключевых файлов (README, манифесты, точки входа), а остальной код читает по требованию через встроенный инструмент поиска `repo_search` в рамках бюджета контекста (по аналогии с Qwen Coder, OpenAI Codex и opencode). Экспорт изменений выполняется в новую ветку **с обязательным Pull Request** — прямые коммиты в основную ветку не выполняются. Отключён по умолчанию; включается переменными `CODER_*` (см. раздел «Работа с Coder»).

- 📱 **Адаптивный дизайн и PWA**: Единый комфортный опыт на desktop, ноутбуках и мобильных устройствах. Progressive Web App даёт ощущение нативного приложения и доступ в офлайн на localhost.

- ✒️🔢 **Полная поддержка Markdown и LaTeX**: Развитые возможности Markdown и LaTeX для более выразительного взаимодействия.

- 🎤📹 **Голос/видеозвонок без рук**: Встроенные звонки с голосом и видео с несколькими провайдерами Speech-to-Text (Local Whisper, OpenAI, Deepgram, Azure) и движками Text-to-Speech (Azure, ElevenLabs, OpenAI, Transformers, WebAPI).

- 💾 **Постоянное хранилище артефактов**: Встроенный API хранилища key-value для артефактов — журналы, трекеры, таблицы лидеров и совместные инструменты с личными и общими областями данных.

- 📚 **Локальная интеграция RAG**: Retrieval Augmented Generation на базе 9 векторных баз данных и нескольких движков извлечения контента (Tika, Docling, Document Intelligence, Mistral OCR, PaddleOCR-vl, внешние загрузчики). Поддерживается гибридный поиск (BM25 + вектор) с reranking и режимом полного контекста. Загружайте документы в чат или забирайте их из вашей библиотеки командой `#`.

- 🔍 **Веб-поиск для RAG**: Ищите в интернете через десятки провайдеров, включая `SearXNG`, `Google PSE`, `Brave Search`, `Kagi`, `Mojeek`, `Tavily`, `Perplexity`, `Firecrawl`, `serpstack`, `serper`, `Serply`, `DuckDuckGo`, `SearchApi`, `SerpApi`, `Bing`, `Jina`, `Exa`, `Sougou`, `Azure AI Search` и `Ollama Cloud`. Результаты сразу внедряются в диалог.

- 🌐 **Возможность веб-просмотра**: Подключайте сайты в чат командой `#` с URL, либо позволяйте модели забирать их самостоятельно, когда это нужно.

- 🎨 **Генерация и редактирование изображений**: Создавайте и редактируйте изображения с несколькими движками, включая OpenAI DALL·E, Gemini, ComfyUI (локально) и AUTOMATIC1111 (локально). Поддерживаются и генерация, и редактирование на основе промптов.

- ⚙️ **Диалоги с несколькими моделями**: Общайтесь сразу с несколькими моделями, параллельно используя их сильные стороны для наиболее качественных ответов.

- 📊 **Аналитика использования и оценка моделей**: Админ-панели отслеживают объём сообщений, потребление токенов и стоимость по пользователям и моделям. Оценивайте модели во встроенной арене, используя A/B тестирование и лидерборды на базе ELO.

- 🗄️ **Гибкие база данных и хранилище**: Выбирайте SQLite (с опциональным шифрованием) или PostgreSQL и храните файлы локально либо в S3, Google Cloud Storage или Azure Blob Storage.

- 🧬 **Расширенная поддержка векторных баз данных**: Выбирайте из 9 векторных баз данных: ChromaDB, PGVector, Qdrant, Milvus, Elasticsearch, OpenSearch, Pinecone, S3Vector и Oracle 23ai.

- 🪪 **Корпоративная аутентификация и развёртывание**: Полная интеграция LDAP/Active Directory, SSO через trusted headers и OAuth-провайдеров, а также автоматизированное SCIM 2.0-подготовление для провайдеров идентификации вроде Okta, Azure AD и Google Workspace.

- ☁️ **Интеграция файлов в облаке**: Нативный выбор файлов из Google Drive и OneDrive/SharePoint, чтобы импорт документов из корпоративного облачного хранилища был бесшовным.

- 🔭 **Наблюдаемость в продакшене**: Встроенная поддержка OpenTelemetry для трассировок, метрик и логов — подключается к вашей текущей системе мониторинга.

- ⚖️ **Горизонтальное масштабирование**: Сессии с Redis и поддержка WebSocket для развертываний с несколькими воркерами и узлами за балансировщиками нагрузки.

- 🌐🌍 **Мультиязычность**: Используйте Open WebUI на предпочитаемом языке благодаря поддержке i18n. Мы активно ищем участников, чтобы расширять покрытие языков!

- 🌟 **Регулярные обновления**: Мы постоянно улучшаем Open WebUI регулярными релизами, исправлениями и новыми возможностями.

- 🛡️ **Прозрачный процесс безопасности**: Отчёты по безопасности разбираются, исправляются и публикуются открытыми advisory через документированный процесс ответственного раскрытия. См. нашу [Security Policy](https://github.com/open-webui/open-webui/security).

## Экосистема Open WebUI 🌐

Open WebUI — это основа: вокруг неё находятся сопутствующие приложения и инфраструктура, которые расширяют возможности вашей ИИ-системы — туда, куда она может дотянуться, и как именно вы её запускаете:

- ⚡ **Open Terminal** ([open-webui/open-terminal](https://github.com/open-webui/open-terminal)): Самостоятельно разворачиваемая вычислительная среда, которая подключается к Open WebUI и даёт ИИ место для написания кода, запуска, чтения вывода, исправления ошибок и итераций прямо в чате.

- 🔒 **Terminals** · Enterprise ([open-webui/terminals](https://github.com/open-webui/terminals)): Изолированные контейнеры на пользователя с отдельными учётными данными, лимитами ресурсов и правилами сети. Автоматическое управление жизненным циклом в Docker или Kubernetes.

- 💻 **cptr** ([open-webui/computer](https://github.com/open-webui/computer)): Самостоятельный компьютер и агент для кодинга в формате “mobile-first”, который работает на вашей собственной машине. Файлы, терминал и git в отдельной вкладке браузера — доступны с вашего телефона. Подключайте его к Open WebUI как модель или используйте через Telegram, WhatsApp и другие сервисы.

- 🔄 **oikb** ([open-webui/oikb](https://github.com/open-webui/oikb)): Питайте ваши базы знаний из 45+ источников (GitHub, Confluence, ServiceNow, Salesforce, Jira, Slack, SharePoint, Notion и др.), поддерживая инструменты, которыми уже пользуется ваша команда, в постоянной синхронизации.

- 🖥️ **Нативное настольное приложение** ([open-webui/desktop](https://github.com/open-webui/desktop)): Запускайте Open WebUI как нативное приложение на macOS, Windows и Linux. Системная панель Spotlight-чата с захватом скриншотов, голосом «push-to-talk» и опциональным полностью локальным выводом через встроенный движок llama.cpp.

Хотите узнать больше? Посетите нашу [документацию Open WebUI](https://docs.openwebui.com) для подробностей!

## Как установить 🚀


### Установка через Python pip 🐍

Open WebUI можно установить с помощью pip, установщика пакетов Python. Перед началом убедитесь, что у вас используется **Python 3.11**, чтобы избежать проблем совместимости.

1. **Установите Open WebUI**:
   Откройте терминал и выполните следующую команду, чтобы установить Open WebUI:


   ```bash
   pip install open-webui
   ```

2. **Запуск Open WebUI**:
   После установки вы можете запустить Open WebUI, выполнив команду:


   ```bash
   open-webui serve
   ```

Это запустит сервер Open WebUI, и вы сможете открыть его по адресу [http://localhost:8080](http://localhost:8080)

### Быстрый старт с Docker 🐳


> [!NOTE]
> Обратите внимание: для некоторых Docker-сред могут потребоваться дополнительные настройки. Если столкнётесь с проблемами подключения, подробное руководство в [документации Open WebUI](https://docs.openwebui.com/) поможет разобраться.

> [!WARNING]
> При установке Open WebUI через Docker обязательно добавьте в команду параметр `-v open-webui:/app/backend/data`. Это критически важно: так база данных корректно смонтируется, что предотвращает потерю данных.

> [!TIP]
> Если вы хотите использовать Open WebUI с включённым Ollama или с ускорением CUDA, рекомендуем применять наши официальные образы с тегами `:cuda` или `:ollama`. Чтобы включить CUDA, нужно установить [Nvidia CUDA container toolkit](https://docs.nvidia.com/dgx/nvidia-container-runtime-upgrade/) в вашей Linux/WSL-системе.


### Установка со стандартной конфигурацией

- **Если Ollama запущен на вашем компьютере**, используйте эту команду:


  ```bash
  docker run -d -p 8083:8080 --add-host=host.docker.internal:host-gateway -v open-webui:/app/backend/data --name open-webui --restart always ghcr.io/open-webui/open-webui:main
  ```

- **Если Ollama размещён на другом сервере**, используйте эту команду:

  Чтобы подключиться к Ollama на другом сервере, измените `OLLAMA_BASE_URL` на URL этого сервера:


  ```bash
  docker run -d -p 8083:8080 -e OLLAMA_BASE_URL=https://example.com -v open-webui:/app/backend/data --name open-webui --restart always ghcr.io/open-webui/open-webui:main
  ```

- **Чтобы запустить Open WebUI с поддержкой Nvidia GPU**, используйте эту команду:

  ```bash

  docker run -d -p 8083:8080 --gpus all --add-host=host.docker.internal:host-gateway -v open-webui:/app/backend/data --name open-webui --restart always ghcr.io/open-webui/open-webui:cuda
  ```

### Установка только для OpenAI API

- **Если вы используете только OpenAI API**, используйте эту команду:


  ```bash
  docker run -d -p 8083:8080 -e OPENAI_API_KEY=your_secret_key -v open-webui:/app/backend/data --name open-webui --restart always ghcr.io/open-webui/open-webui:main
  ```

### Установка Open WebUI с встроенной поддержкой Ollama

Этот способ установки использует один образ контейнера, в который уже включены Open WebUI и Ollama — так настройка выполняется одной командой. Выберите подходящую команду в зависимости от вашей конфигурации оборудования:

- **С поддержкой GPU**:
  Используйте ресурсы графического процессора, выполнив команду:


  ```bash
  docker run -d -p 8083:8080 --gpus=all -v ollama:/root/.ollama -v open-webui:/app/backend/data --name open-webui --restart always ghcr.io/open-webui/open-webui:ollama
  ```

- **Только CPU**:
  Если вы не используете GPU, вместо этого выполните команду:


  ```bash
  docker run -d -p 8083:8080 -v ollama:/root/.ollama -v open-webui:/app/backend/data --name open-webui --restart always ghcr.io/open-webui/open-webui:ollama
  ```

Обе команды обеспечивают встроенную, простую установку Open WebUI и Ollama, чтобы всё можно было быстро запустить.

После установки вы сможете открыть Open WebUI по адресу [http://localhost:8083](http://localhost:8083). Удачи! 😄

### Развёртывание единым Docker-стеком 📦

Помимо одиночных `docker run`, проект поставляется с `docker-compose.yaml`, который
поднимает **все три сервиса в одном стеке** и одной сети:

| Сервис | Образ | Назначение |
|---|---|---|
| `open-webui` | `open-webui-uncensored:local` (сборка из этого репо) | Веб-интерфейс, порт `${OPEN_WEBUI_PORT:-8083}` |
| `neo4j` | `neo4j:5.26` | GraphRAG для `retrieval/graphrag`, bolt только на loopback |
| `studio` | `uncensored-studio:local` (сборка из `studio/`) | Uncensored AI Studio: LLM/Whisper/SD/Kokoro, OpenAI-совместимый API |

```bash
docker compose up -d --build
docker compose down
```

То же самое делает `./docker-run.sh` — это рекомендуемая точка входа: он
проверяет наличие `.env` и плагина Compose, затем вызывает
`docker compose up -d --build --pull always` и ждёт готовности `open-webui`
(подробности — в [START.md](START.md)).

Тома `open-webui` и `neo4j-data` объявлены `external` и привязаны к существующим
`open-webui-rus_open-webui` / `open-webui-rus_neo4j-data` — поэтому переезд с
`docker-run.sh` на compose **не теряет** `webui.db`, `.webui_secret_key` (сессии
выживают), индексы chroma и загруженные файлы. Настройки читаются из `.env`
(см. раздел «Deployment settings come from `.env`» в [TROUBLESHOOTING.md](TROUBLESHOOTING.md)).

Студия не копирует бинарники в образ — весь `studio/app` (node-runtime, бэкенды,
модели в `app/models/`, `app/llm-models/`, `app/openvino-models/`,
`app/speech-models/`, `app/tts-models/` и выводы в `app/outputs/`,
`app/tts-outputs/`) пробрасывается **bind mount** как `/app` и остаётся на диске
хоста. Корневой `.dockerignore` исключает `studio/` из контекста сборки WebUI, а
`studio/.dockerignore` — `app/` из контекста сборки студии (иначе в builder
улетает 249 GB).

**Подключение студии как источника моделей.** llama-server студии слушает
`10086` на всех интерфейсах, а Open WebUI ходит к нему по имени сервиса через
общую сеть стека. В **Admin → Settings → Connections** добавьте External OpenAI
API connection с базой `http://uncensored-studio:10086/v1` — после этого модели
из `app/llm-models/` появляются в списке. Модель загружается в llama-server по
первому запросу (студия не стартует её автоматически — нужен один чат-запрос
через UI студии на `http://localhost:14200`, либо переключение туда).

## Работа с GrafRAG / RAG

### 1. Убедитесь, что RAG включён
- Установите переменную окружения `VECTOR_DB` в ваш векторный магазин (например, `valkey`).
- Добавьте нужные параметры, например:
  ```env
  VECTOR_DB=valkey
  VALKEY_URL='valkey://localhost:6379'
  ```
- **Важно:** `VECTOR_DB=valkey` работает только при двух одновременных условиях:
  1. в образе установлен клиент `valkey-glide-sync` (в `backend/requirements.txt` он
     закомментирован как optional — раскомментируйте строку и пересоберите образ);
  2. по адресу `VALKEY_URL` действительно отвечает сервер Valkey.
  Иначе приложение падает на старте с `ImportError: valkey-glide-sync is required when
  VECTOR_DB=valkey`, а `restart: always` превращает это в бесконечный crash-loop
  (контейнер не поднимается, UI недоступно). По умолчанию используется `chroma`,
  которого достаточно для старта — он хранит индексы в томе `data` рядом с `webui.db`.
- Перезапустите контейнер, чтобы изменения вступили в силу.

### 2. Доступ к UI RAG
- Откройте Open WebUI в браузере (по‑умолчанию `http://localhost:8083`).
- В левом меню выберите пункт **Knowledge** (или **RAG**).
- Нажмите **Create New Knowledge** для создания новой коллекции.

### 3. Загрузка документов
- Перетащите файлы в область загрузки или используйте кнопку **Upload**. Можно перетащить целую папку — её структура вложений будет воссоздана, а не «сплющена» в набор разрозненных файлов.
- Поддерживаемые форматы: `.txt`, `.pdf`, `.docx` и др. При загрузке автоматически будет выполнено встраивание (embedding) выбранной модели.
- Под именем каждого файла отображается **прогресс-бар**: первая половина — фактическая передача байтов на сервер, вторая — обработка и встраивание на стороне бэкенда (счётчик «Встраивание фрагментов N/M»). Прогресс продолжается даже в другой вкладке или после перезагрузки страницы; зависших на «Uploading 0%» строк больше не бывает — сбойная загрузка убирается из списка, а ошибка отражается в записи файла.
- Файлы в статусах *pending* / *processing* можно **отменить** («Cancel embedding») — отмена действительно останавливает фоновый конвейер и очищает уже записанные векторы, файл не «воскресает» как завершённый.
- **Повторные документы не переэмбедятся.** Если хэш извлечённого текста совпадает с уже проиндексированным файлом, его векторы копируются, а не вычисляются заново (экономия ~12.5 с на CPU-эндпоинте за каждый чанк). Повторное использование возможно только при совпадении движка и модели эмбеддинга источника — при любом несоответствии выполняется обычное встраивание. Управляется настройкой `RAG_DEDUP_DUPLICATE_FILES` (по умолчанию включена).

### 4. Нагрузка на сервер эмбеддингов
- Запросы на встраивание ограничены по параллелизму и по времени одного HTTP-вызова, чтобы «зависший» сервер не держал файл в статусе *processing* вечно.
- `RAG_EMBEDDING_BATCH_SIZE` — чанков на один запрос; по умолчанию `1`, так как большие батчи на медленном (CPU) эндпоинте выглядят как замороженный прогресс-бар, а занятой Ollama отвечают `503 server busy`.
- `RAG_EMBEDDING_CONCURRENT_REQUESTS` — максимум одновременных запросов; при значении `0` применяется безопасный лимит по умолчанию (`RAG_EMBEDDING_CONCURRENT_REQUESTS_FALLBACK`, по умолчанию `4`). Для GPU-эндпоинта оба значения можно явно увеличить в Admin → Settings.

### 5. Конфигурация развёртывания: `.env` — единственный источник настроек

Все настройки контейнерного запуска объявляются один раз — в файле `.env` в корне репозитория (`VECTOR_DB`, `VALKEY_URL`, `NEO4J_*`, `PORT`, `OLLAMA_BASE_URL` и т.д.):

- Файл монтируется в контейнер и читается двумя слоями: `backend/start.sh` парсит его перед запуском uvicorn (`PORT`, `FORWARDED_ALLOW_IPS`), а `open_webui/env.py` перечитывает его и ставит объявленные в нём значения **выше** хранимой таблицы `config`. Имя, объявленное в `.env`, больше не может «пережить» устаревшую запись в базе.
- Переменные, которых в файле нет, по-прежнему полностью управляются из **Admin → Settings**, и сохранение настроек там работает как раньше. Если же имя объявлено в файле, правка из админки действует до следующего перезапуска (после которого файл снова становится источником истины).
- В `docker-compose.yaml` и `docker-compose.ollama.yaml` намеренно нет блоков `environment:` / `env_file:` с дублированием этих имён — они бы молча перекрывали описанный механизм.
- Другой файл настроек: `ENV_FILE=.env.staging docker compose up -d` (подставляется на стороне хоста и монтируется по фиксированному пути в контейнере).

### 6. Выполнение запроса с RAG
- Перейдите в чат.
- Для обращения к базе знаний используйте префикс `#`:
  ```
  #my_knowledge "Какова основная идея загруженного PDF?"
  ```
- Модель выполнит поиск релевантных фрагментов и включит их в ответ.

#### 6.1. Адаптивный RAG-оркестратор (динамическая композиция стратегий)
Поиск больше не статичен: каждый запрос проходит цикл **Preprocessing → Query
Understanding → Policy / Confidence / Planner → Execution (native | hybrid |
graph | agentic | tool) → Evaluation → Synthesis**, и пайплайн подбирается под
тип вопроса — от дешёвого векторного ответа на простой факт до графового обхода
для multi-hop и ограниченного агентного цикла для сложных задач. Полное
описание архитектуры, все переменные окружения (`RAG_ORCHESTRATOR_ENABLED`,
`ORCH_*`, `GRAPHRAG_*`) и пороги маршрутизации — в
[docs/RAG-ORCHESTRATOR.md](docs/RAG-ORCHESTRATOR.md); исходное ТЗ — в
[docs/RAG-ТЗ.md](docs/RAG-ТЗ.md).

Ключевые гарантии:
- **Отказоустойчивость:** при любом сбое оркестрации запрос автоматически
  выполняется прежним базовым путём (вектор/hybrid); одним флагом
  `RAG_ORCHESTRATOR_ENABLED=false` система возвращается к доперестроечному
  поведению.
- **Безопасность (zero-trust):** анти-injection скрининг, изоляция кэша по
  tenant и правам, ACL-ограниченный обход графа, маркировка непроверенных
  внешних результатов.
- **Объяснимость:** каждый ответ имеет статус (`answered / uncertain /
  clarification / refused`), цитаты и полную трассу решения в
  `DATA_DIR/orchestrator.db`; обратная связь пользователей используется для
  калибровки будущей маршрутизации.
- **Наблюдаемость для администратора:** API `/api/v1/graphrag/orchestrator/*`
  — трассы, explain-панель «почему такой ответ», метрики дрейфа (latency p50/p95,
  доли отказов, groundedness по пайплайнам), policy-as-code и горячая смена
  настроек; shadow-режим (`ORCH_SHADOW_PERCENT`) для безопасного A/B-раскатывания.
- **Качество retrieval из коробки:** дешёвый query rewrite (декомпозиция
  составных вопросов) без LLM-вызовов, опциональные cross-encoder rerank и
  LLM-judge groundedness, персистентный кэш ответов и circuit breaker к Neo4j
  (зависимость пропускается после серии отказов вместо оплаты таймаута каждым
  запросом).

### 7. Визуализация GrafRAG
- После нескольких запросов откройте вкладку **Graph** внутри представления коллекции.
- Вы увидите граф, где узлы – документы/фрагменты, а рёбра – семантическая схожесть.

  - Параметры адаптивного оркестратора — под префиксом `rag.orchestrator.*` (например `rag.orchestrator.agentic_enabled`, `rag.orchestrator.conf_single`, `rag.orchestrator.max_latency_ms`); применяются на горячую, без рестарта. Полный перечень env-дефолтов и порогов — в [docs/RAG-ORCHESTRATOR.md](docs/RAG-ORCHESTRATOR.md).
- После изменения параметров рекомендуется перезапустить бэкенд. Если имя переменной объявлено в `.env`, значение из файла имеет приоритет над сохранённой настройкой (см. раздел «Конфигурация развёртывания»).

## Работа с Coder

**Coder** — собственный раздел форка для агентной работы с кодом GitHub-репозиториев (полное техническое задание: [`Coder.md`](./Coder.md)). Раздел **отключён по умолчанию** и не виден в интерфейсе, пока не включён переменными окружения.

Пункт **Coder** в левом меню открывает раздел **в отдельном окне браузера** (`window.open`) как самостоятельное приложение: на маршруте `/coder` основное боковое меню полностью скрыто, интерфейс состоит из двух вкладок — **Workspace** (рабочее пространство: репозиторий, файлы, чат, экспорт) и **Окружение** (список подключённых репозиториев GitHub для выбора целевого проекта).

### 1. Включение и конфигурация

Все настройки передаются через `.env` (единый источник настроек, см. раздел «Конфигурация развёртывания» выше):

```env
CODER_ENABLED=true
CODER_GITHUB_CLIENT_ID=<client_id OAuth-приложения GitHub>
CODER_GITHUB_CLIENT_SECRET=<client_secret OAuth-приложения GitHub>
CODER_ENCRYPTION_KEY=<случайная строка не короче 32 символов>
```

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CODER_ENABLED` | `false` | Feature flag раздела: управляет видимостью пункта меню и доступом API |
| `CODER_GITHUB_CLIENT_ID` / `CODER_GITHUB_CLIENT_SECRET` | пусто | Креденшелы GitHub OAuth App (только GitHub Cloud) |
| `CODER_GITHUB_API_BASE_URL` | `https://api.github.com` | Базовый URL REST API GitHub |
| `CODER_ENCRYPTION_KEY` | пусто | Ключ AES-256-GCM для шифрования OAuth-токенов в БД; при пустом значении используется производный от `WEBUI_SECRET_KEY` |
| `CODER_MAX_FILES_PER_CHANGESET` | `20` | Максимум файлов в одном Change Set |
| `CODER_MAX_FILE_SIZE` | `1048576` (1 МиБ) | Максимальный размер одного файла в изменениях |
| `CODER_MAX_TOTAL_DIFF_SIZE` | `3145728` (3 МиБ) | Суммарный лимит размера diff |
| `CODER_MAX_DIFF_LINES` | `4000` | Максимум строк diff на файл |

> [!WARNING]
> Код читает **только** переменные из таблицы выше. В .env не должно быть
> `CODER_GITHUB_PROVIDER`, `CODER_GITHUB_APP_ID`, `CODER_GITHUB_APP_PRIVATE_KEY_PATH`,
> `CODER_GITHUB_BASE_URL`, `CODER_GITHUB_ENTERPRISE_MODE`, `CODER_MAX_FILE_SIZE_BYTES`,
> `CODER_MAX_TOTAL_CHANGES_BYTES`, `CODER_MAX_FILES_PER_EXPORT`, `CODER_REQUIRE_PULL_REQUEST`,
> `CODER_SECRET_SCANNING_MODE`, `CODER_AUDIT_RETENTION_DAYS`, `CODER_DEFAULT_MODEL` — их
> бэкенд (`config.py` / `utils/coder/`) не читает, они не влияют на поведение. Это пережиток
> ТЗ из `Coder.md`. Лимиты задаются именно как `CODER_MAX_FILE_SIZE`,
> `CODER_MAX_TOTAL_DIFF_SIZE`, `CODER_MAX_FILES_PER_CHANGESET`; база API — только через
> `CODER_GITHUB_API_BASE_URL`.

После изменения переменных перезапустите контейнер. Схема БД обновляется автоматически при старте (миграция Alembic создаёт таблицы `coder_github_connection`, `coder_project`, `coder_export_job`, `coder_audit_event`).

### 2. GitHub OAuth-приложение

В разделе **Settings → Developer settings → OAuth Apps** на GitHub создайте приложение и укажите **Authorization callback URL**:

```
http://<ваш-хост>/api/v1/coder/github/auth/callback
```

(для локального запуска по умолчанию — `http://localhost:8083/api/v1/coder/github/auth/callback`). Скопируйте Client ID и Client Secret в `.env`. Никаких других способов подключения аккаунта (например, PAT-ввода) раздел не поддерживает — только OAuth.

### 3. Основной рабочий процесс

1. Откройте пункт **Coder** в левом меню — раздел откроется **в отдельном окне браузера** как самостоятельное приложение (боковое меню основного окна при этом скрыто). Нажмите **Подключить GitHub** — произойдёт редирект на OAuth и возврат в раздел с установленным соединением. Токен хранится **только на сервере** в зашифрованном виде; в браузере он не появляется.
2. Перейдите на вкладку **Окружение** и выберите нужный репозиторий из списка подключённых. Репозиторий автоматически подгружается в рабочее пространство (**Workspace**): загружаются ветки, дерево файлов и содержимое ключевых исходных файлов, которые попадают в контекст модели — она «видит» код репозитория при ответе. При необходимости просмотрите дерево файлов и содержимое файлов (загружаются по требованию); выбор файла во Workspace выполняется через панель репозитория (ветка и файлы загружаются автоматически при открытии).
3. Задайте задачу в чате. Для сброса истории и контекста нажмите кнопку **Clear chat** (Очистить чат). Рекомендуется выбирать специализированные кодовые модели (Qwen-Coder, DeepSeek-Coder, Starpilot и т.п.) — селектор моделей подсвечивает подходящие. Ответ модели может содержать **Change Set** — структурированный JSON со списком действий `create` / `update` / `delete` над файлами.
4. Изменения проходят **серверную валидацию**: запрещены выход за пределы репозитория (`..`, абсолютные пути, `.git/`), превышение лимитов размера и числа файлов. Для каждого изменённого файла показывается unified diff.
5. Нажмите **Экспорт**: изменения коммитятся в **новую ветку** через Git Data API, после чего **обязательно создаётся Pull Request** — прямые записи в основную ветку исключены конструкцией раздела. Диалог экспорта требует явного подтверждения пользователем; по завершении выводятся ссылки на коммит и PR. Повторный запуск с теми же параметрами идемпотентен (не создаёт дублей благодаря ключу идемпотентности).
6. Все значимые действия (подключение, экспорт, ошибки) пишутся в журнал аудита `coder_audit_event`, доступный через API `/api/v1/coder/audit`.

### 4. Работа с большими репозиториями (более 25 файлов)

Для репозиториев любого размера применяется **прогрессивная загрузка контекста** — подход, заимствованный у лучших агентов кодинга (Qwen Coder, OpenAI Codex, opencode): вместо попыток поместить весь код в промпт модель получает «карту» репозитория и читает код по требованию.

1. **Полное дерево файлов** всегда передаётся модели — она знает все пути, даже если содержимое файлов не загружено.
2. **Скелетная загрузка**: при выборе репозитория во вкладке «Окружение» автоматически загружается не произвольные первые N файлов, а ~12 ключевых: `README`, манифесты (`package.json`, `pyproject.toml`, `go.mod` и т.п.) и точки входа в каждом каталоге. Это даёт модели понимание архитектуры проекта.
3. **Бюджет контекста (~48 000 символов на сообщение)**: ~60% бюджета отводится на список файлов, ~40% — на содержимое скелета. При переполнении лишнее обрезается с явной пометкой, что файл доступен по запросу, — модель никогда не делает вывод, что файла «нет».
4. **Инструмент `repo_search` (grep-style on-demand reading)**: если модели нужен дополнительный код, она emit-ит структурированный запрос в блоке ` ```repo_search ` (query, glob, max_results), бэкенд выполняет серверный поиск по содержимому репозитория (`GET /api/v1/coder/search`) и возвращает сниппеты с номерами строк в том же цикле агентного хода (до 3 поисков за ход). Модель может также явно попросить конкретный файл — он пакетно догружается через `POST /api/v1/coder/files/batch`.
5. **Ручное прикрепление**: любой файл можно открыть во Workspace и прикрепить к сообщению — его полное содержимое будет включено в контекст запроса.

Таким образом, размер репозитория не ограничен 25 файлами: в контексте одновременно живёт только релевантный фрагмент кода, а остальное доступно модели мгновенно через поиск.

### 5. Ограничения и безопасность

- Поддерживается только GitHub Cloud; self-hosted GitHub Enterprise — вне объёма MVP.
- Контекст файлов, вставляемый в промпт, помечается как недоверенный (защита от prompt-injection из содержимого репозитория).
- Секреты клиента OAuth и пользовательские токены никогда не отдаются фронтенду; все вызовы GitHub API выполняются бэкендом.
- Экспорт возможен только при наличии валидного Change Set и подтверждении пользователя; PR обязателен даже для репозиториев без защиты веток.

#### Open WebUI: ошибка соединения с сервером

Если у вас возникают проблемы с подключением, часто причина в том, что Docker-контейнер WebUI не может достучаться до сервера Ollama по адресу 127.0.0.1:11434 (host.docker.internal:11434) внутри контейнера. Чтобы исправить это, добавьте в команду Docker флаг `--network=host`. Обратите внимание: порт меняется с 8083 на 8080, поэтому ссылка будет `http://localhost:8080`.


**Example Docker Command**:

```bash
docker run -d --network=host -v open-webui:/app/backend/data -e OLLAMA_BASE_URL=http://127.0.0.1:11434 --name open-webui --restart always ghcr.io/open-webui/open-webui:main
```

### Обновляйте Docker-установку

Смотрите руководство по обновлениям в нашей [документации Open WebUI](https://docs.openwebui.com/getting-started/updating).


### Использование ветки Dev 🌙

> [!WARNING]
> Ветка `:dev` содержит самые свежие нестабильные возможности и изменения. Используйте её на свой риск: возможны ошибки или неполностью завершённые функции.

Если вам хочется попробовать самые новые «краевые» возможности и вы нормально относитесь к редкой нестабильности, можно использовать тег `:dev` так:


```bash
docker run -d -p 8083:8080 -v open-webui:/app/backend/data --name open-webui --add-host=host.docker.internal:host-gateway --restart always ghcr.io/open-webui/open-webui:dev
```

### Режим офлайн

Если Open WebUI запущен в среде без доступа в интернет, задайте переменную окружения `HF_HUB_OFFLINE` равной `1`, чтобы предотвратить попытки скачивать модели из интернета.


```bash
export HF_HUB_OFFLINE=1
```
